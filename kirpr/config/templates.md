# Шаблоны и правила декомпозиции

## Критические правила (общие для всех команд)

- **Один вопрос за раз.** Не задавай несколько вопросов в одном сообщении.
- **Предлагай варианты.** Где возможно — давай пронумерованные варианты ответа.
- **Покажи diff перед записью.** Никогда не записывай файлы без подтверждения пользователя.
- **Кодовая база — источник правды.** Если подзадача описывает путь/структуру, которой нет в коде — это `критично`.
- **Не изобретай проблемы.** Если подзадача чётко написана и соответствует коду — не нужно искать проблемы ради отчёта.
- **Используй шаблоны ниже.** Новые секции и файлы — по этим шаблонам.

## Загрузка контекста декомпозиции

Паттерн загрузки для `/kirpr:tasks-review` и `/kirpr:tasks-adapt`:

### Вариант A: `.context.md` существует (быстрый путь)
1. Прочитай `{dir}/.context.md` — кэш контекста из прошлой сессии.
2. Прочитай `{dir}/00-overview.md` — навигационный индекс.
3. Дальнейшие файлы — по необходимости (зависит от scope команды).
4. **Не запрашивай трекер API** — данные уже в `.context.md`. Если нужны детали YouTrack description — читай `{dir}/source.md`.

### Вариант B: `.context.md` не существует (fallback)
1. Прочитай `{dir}/source.md` и `{dir}/00-overview.md`.
2. Прочитай все файлы `{dir}/*.md`.
3. Прочитай `~/.claude/kirpr/config/tracker.md` для определения скрипта трекера. Загрузи данные задачи.
4. Сообщи пользователю: "Файл `.context.md` не найден — загружаю полный контекст."

## Правила нейминга файлов

- **Директория:** lowercase номер задачи (например `sas-200/`)
- **Обзор:** `00-overview.md`
- **Подзадачи:** `XX-Y-name.md` где:
  - `XX` — номер фазы (01, 02, 03...)
  - `Y` — номер подзадачи внутри фазы (опционально, через дефис)
  - `name` — короткое имя на английском (kebab-case)
  - Примеры: `01-schema.md`, `02-1-domain-model.md`, `02-2-manager-crud.md`
- **Язык файлов:** имена на английском, содержимое на русском

## Шаблон подзадачи XX-Y-name.md

```markdown
## Задача X.Y — {Название} [{сервис/модуль}, ~{N}ч]

{1-2 предложения: что делает эта задача и какой файл/модуль создаёт/изменяет.}

### 1. {Первый блок реализации}

{Описание: что конкретно нужно сделать.}
{Код, SQL, структуры данных — если уместно.}

### 2. {Второй блок реализации}

{...}

### N. {Последний блок}

{...}

Критерий готовности: {конкретное условие — компиляция, тесты, интеграция.}
```

**Правила для содержимого подзадач:**
- Каждая подзадача — самодостаточная. Разработчик может взять файл и выполнить задачу, не читая остальные.
- Ссылки только на номер основной задачи и на предыдущие подзадачи.
- Код-примеры там, где они помогают понять структуру (Go structs, SQL, API contracts).
- Критерий готовности — конкретный и проверяемый.
- Оценка трудозатрат реалистична (<= 4 часов).

- Файл создаётся автоматически, не показывается пользователю для ревью.
- Файл добавлен в `.gitignore` — это кэш, не артефакт.

## Рубрика Quality Scoring

Используется в `/kirpr:tasks-review` для оценки каждой подзадачи. 5 критериев, 0-2 балла каждый = max 10.

**Порог качества: 8/10.** Файлы с score < 8 требуют итерации.

### К1: Конкретность (0-2)

Оценивает однозначность формулировок и отсутствие расплывчатых выражений.

- **0** — Формулировки абстрактные ("добавить логику обработки", "реализовать валидацию"). Разработчик вынужден интерпретировать scope.
- **1** — Основные шаги конкретны, но есть пробелы (1-2 места с "и т.д.", "аналогично", без деталей).
- **2** — Каждый шаг однозначен. Два разработчика реализовали бы одинаково.

### К2: Техническая полнота (0-2)

Оценивает наличие необходимых технических деталей: типы, сигнатуры, SQL, структуры данных.

- **0** — Нет код-примеров, структур данных, SQL. Только текстовое описание.
- **1** — Ключевые структуры/сигнатуры есть, но не все. Или есть примеры, но неполные.
- **2** — Все важные типы, сигнатуры, SQL, примеры YAML/JSON приведены. Код-примеры готовы к copy-paste.

### К3: Тестируемость (0-2)

Оценивает критерий готовности и покрытие тестами.

- **0** — Критерий готовности отсутствует или непроверяемый ("всё работает", "функционал реализован").
- **1** — Критерий проверяемый, но нет указания на edge cases или test scenarios.
- **2** — Критерий конкретный + перечислены test cases / edge cases / ожидаемое поведение при ошибках.

### К4: Самодостаточность (0-2)

Оценивает, может ли разработчик выполнить задачу по этому файлу, не читая остальные.

- **0** — Необходимо читать 3+ других файлов для понимания контекста. Implicit зависимости.
- **1** — Зависимости указаны, но часть контекста приходится искать в других файлах.
- **2** — Файл полностью самодостаточен. Зависимости явно перечислены с ссылками. Весь нужный контекст inline.

### К5: Соответствие кодовой базе (0-2)

Оценивает совпадение описанных путей, структур и конвенций с реальным кодом.

- **0** — 2+ несуществующих путей/пакетов, или противоречие с реальными конвенциями.
- **1** — Пути существуют, но стиль (naming, тесты, паттерны) не совпадает с существующим кодом.
- **2** — Все пути, структуры и конвенции соответствуют кодовой базе. Предложенный код идиоматичен.
