# kirpr-flow — рабочий цикл разработки без git

Скил `kirpr-flow` — зонтичная замена набору superpowers: тот же цикл «идея →
спека → план → исполнение субагентами → ревью → финал», но без единой git-операции
и с жёстким контрактом верификации.

## Цель

Дать один вызов, который ведёт работу от формулировки идеи до сданного
результата, не касаясь системы контроля версий и не позволяя объявить работу
сделанной без предъявленного доказательства.

## Ограничения

Три ограничения заданы пользователем и не обсуждаются внутри реализации.

**1. Никаких git-операций.** Ни пишущих, ни читающих. Запрещены `git commit`,
`git branch`, `git worktree`, `git merge`, `git push`, `git stash`, а равно
`git diff`, `git log`, `git status`, `git rev-parse` и чтение содержимого
каталога `.git/`. Запрет распространяется на косвенные пути: `gh`, `jj`,
MCP-инструменты вида `mcp__goland__git_status` и `mcp__webstorm__git_status`.
Решения о коммите, слиянии, откате и публикации принимает пользователь вне
набора.

**2. Четыре формата верификации.** Работа не считается сделанной, пока не
предъявлено доказательство в одном из форматов:

| Что сделано | Чем доказывается |
|---|---|
| Написан код | Тест, покрывающий этот код. Допускается временный |
| Написан скрипт | Запуск скрипта |
| Изменена БД | Запрос к БД, показывающий результат |
| Написан или обновлён документ | Чтение документа целиком |

**3. Subagent-driven development сохраняется.** Исполнение плана свежим
субагентом на задачу, ревью после каждой задачи и широкое ревью в конце —
центральный режим набора, а не опция.

## Что выброшено и почему

| Скил оригинала | Судьба |
|---|---|
| `using-git-worktrees` | Выброшен целиком. Изоляции нет: работаем в текущем рабочем дереве, за его готовность отвечает пользователь |
| `finishing-a-development-branch` | Заменён режимом `finish`, который не трогает git: сводка сделанного, список принятых решений, список отложенных замечаний |
| Скрипты `sdd-workspace`, `task-brief`, `review-package` | Выброшены. Набор состоит только из markdown-файлов |

`review-package` отмирает вместе с диффами: ревью строится на чтении файлов
целиком. `task-brief` отмирает потому, что план пишется каталогом с отдельным
файлом на задачу — вырезать нечего. `sdd-workspace` отмирает потому, что
резолвить корень репозитория без `git rev-parse` незачем: пути артефактов
фиксированы относительно текущего рабочего каталога.

## Структура

```
skills/kirpr-flow/
  SKILL.md                 роутер: разбор аргумента, карта режимов, инвариант «git нет»
  core/rules.md            запрет git и четыре формата верификации
  core/tests.md            TDD и признаки честного теста
  core/subagents.md        диспетчеризация субагентов
  core/feedback.md         приём замечаний ревьюера
  core/artifacts.md        имена и расположение артефактов
  modes/brainstorm.md      идея → спека
  modes/plan.md            спека → план каталогом
  modes/execute.md         исполнение субагентами
  modes/execute-inline.md  исполнение в текущей сессии, без субагентов
  modes/review.md          заказ ревью
  modes/debug.md           системный разбор бага
  modes/finish.md          финал без git
  modes/skill.md           написание и правка скилов
  prompts/implementer.md
  prompts/task-reviewer.md
  prompts/re-review.md
  prompts/code-reviewer.md
  prompts/spec-reviewer.md
  prompts/plan-reviewer.md
```

Пути к `core/*.md`, `modes/*.md` и `prompts/*.md` — относительно каталога
`SKILL.md`, как в `expert-panel` и `grill-me`.

Роль файла определяется тем, кто его читает. Режим читает пользовательский
поток управления. `core/` читают и режим, и субагент — это общие правила.
`prompts/` — шаблоны, которые режим заполняет и отдаёт субагенту.

## Соответствие оригиналу

| Скил superpowers | Куда лёг |
|---|---|
| `using-superpowers` | `SKILL.md` |
| `brainstorming` | `modes/brainstorm.md` |
| `writing-plans` | `modes/plan.md` |
| `subagent-driven-development` | `modes/execute.md` + `prompts/` |
| `executing-plans` | `modes/execute-inline.md` |
| `requesting-code-review` | `modes/review.md` + `prompts/code-reviewer.md` |
| `receiving-code-review` | `core/feedback.md` |
| `test-driven-development` (+ `writing-good-tests`) | `core/tests.md` |
| `verification-before-completion` | `core/rules.md` |
| `dispatching-parallel-agents` | `core/subagents.md` |
| `systematic-debugging` | `modes/debug.md` |
| `writing-skills` | `modes/skill.md` |

Двенадцать скилов покрыты. Разложены по ролям, а не один-в-один в файлы:
`verification-before-completion` и `test-driven-development` никто не вызывает
отдельно — они действуют внутри имплементера и ревьюера, поэтому стали
правилами, а не режимами.

## Вызов

```
/kirpr-flow brainstorm <тема или путь к файлу>
/kirpr-flow plan <путь к спеке>
/kirpr-flow execute <путь к каталогу плана>
/kirpr-flow execute --inline <путь к каталогу плана>
/kirpr-flow review <путь к каталогу плана | пути к файлам>
/kirpr-flow debug <симптом>
/kirpr-flow finish
/kirpr-flow skill <имя скила>
```

Разбор аргументов в `SKILL.md`:

- Распознавание идёт по началу строки, а не по одному первому слову: строка
  `execute --inline` проверяется раньше строки `execute`, иначе двухтокенный
  режим недостижим — первое слово совпало бы с однотокенным `execute`, и
  `--inline` уехал бы в аргумент.
- Начало строки совпало с именем режима — читай соответствующий `modes/*.md`
  и следуй ему. Остаток строки — аргумент режима.
- Ничего не совпало — спроси, какой режим нужен. Не угадывай.
- Аргументов нет — спроси, что делаем. Не угадывай по содержимому
  репозитория.
- Аргумент режима похож на путь, но по нему ничего нет — скажи это и спроси,
  что имелось в виду.

`SKILL.md` держит инвариант, который действует во всех режимах: git запрещён,
верификация обязательна, артефакты лежат по фиксированным путям. Полные
формулировки — в `core/rules.md`, `SKILL.md` даёт выжимку и ссылку.

## Артефакты

```
docs/kirpr-flow/specs/YYYY-MM-DD-<тема>-design.md
docs/kirpr-flow/plans/YYYY-MM-DD-<тема>/
  00-overview.md            цель, архитектура, глобальные ограничения, путь к спеке
  task-01.md … task-NN.md   задачи
  progress.md               ledger
  reports/task-NN.md        отчёты имплементеров
```

Каталог `docs/kirpr-flow/` заводится отдельно от существующего
`docs/superpowers/`, чтобы артефакты двух наборов не смешивались.

Ничего из этого не удаляется в конце работы: отчёты и ledger — часть
результата, а не временный мусор. Оригинал удалял свой workspace, потому что
запись оставалась в истории коммитов; здесь истории нет, поэтому запись
остаётся файлами. Набор не создаёт и не правит `.gitignore` — это git-операция
и решение пользователя.

## Язык и установка

Файлы набора пишутся на русском, как `expert-panel` и `grill-me`. Английскими
остаются: имена файлов и каталогов, имена режимов в строке вызова, значения
статусов в отчёте (`DONE`, `DONE_WITH_CONCERNS`, `NEEDS_CONTEXT`, `BLOCKED`) и
уровни находок (`Critical`, `Important`, `Minor`) — по ним контроллер и
ревьюер сверяются машинально, и перевод сделал бы их менее надёжными. Туда
же относится `ledger`: это название журнала работы, оно встречается в
`core/artifacts.md`, `modes/execute.md` и `modes/finish.md`, и разнобой
«ledger/журнал» между файлами дороже одного английского слова.

`install.sh` дополняется установкой `kirpr-flow`: каталог
`~/.claude/skills/kirpr-flow/` с подкаталогами `core/`, `modes/`, `prompts/`,
по образцу того, как ставятся `expert-panel` и `grill-me`. Старая установка
удаляется перед копированием. Пользовательских файлов, которые нужно
сохранять между установками (как `custom-experts.md` у панели), у набора нет.
`uninstall.sh` дополняется удалением того же каталога.

## core/rules.md

Единственное место, где сформулированы два глобальных правила. Содержит:

**Запрет git.** Полный перечень запрещённых команд и косвенных путей.
Отдельным пунктом — что делать, когда план или привычка требуют коммит: шаг
пропускается, факт уходит строкой в ledger и в финальную сводку. Не
подменять коммит архивом, копией каталога или `patch`-файлом «на всякий
случай»: это тот же обход другими средствами.

**Четыре формата верификации.** Таблица форматов, что считается
доказательством, и пятый случай — ловушка.

Доказательство — это команда и её вывод. Не пересказ вывода, не «тесты
зелёные», не «должно работать», не «я проверил». Для формата «документ»
доказательство — чтение файла целиком и результат по чеклисту: остались ли
плейсхолдеры, есть ли внутренние противоречия, есть ли места с двумя
прочтениями.

**Прямая просьба.** Если пользователь просит закоммитить, создать ветку или
слить прямо в разговоре, набор этого не делает и говорит почему: git вне его
границ. Это не отказ помочь — пользователь выполняет операцию сам, а набор
отдаёт ему всё, что для неё нужно: список изменённых файлов и сводку из
`modes/finish.md`.

**Пятый случай.** Изменение, к которому не подходит ни один из четырёх
форматов — правка конфига, обновление зависимости, удаление мёртвого кода, —
не даёт права написать «верификация неприменима». Исполнитель обязан либо
назвать ближайший формат и то, как он его применил, либо вернуть статус
BLOCKED. Формулировка «неприменимо» — самая частая форма пропущенной
проверки, и она запрещена явно.

**Выжимка для промптов.** Дословный блок, который вставляется в тело каждого
dispatch-промпта до всего остального:

```
Git запрещён полностью: ни commit, ни branch, ни diff, ни log, ни status.
Если задача требует коммит — не коммить, напиши это в отчёт.
Работа не сделана, пока не предъявлено доказательство одного из четырёх
форматов: код → тест, скрипт → запуск, БД → запрос, документ → чтение целиком.
Доказательство — команда и её вывод в отчёте. Пересказ доказательством не является.
Детали: ~/.claude/skills/kirpr-flow/core/rules.md
```

Дублирование выжимки и файла намеренное: выжимка работает, даже если субагент
не открыл файл, а файл держит формулировку в одном месте при правке правила.

## core/tests.md

Порт `test-driven-development` и `writing-good-tests`. Тест пишется первым,
прогоняется до реализации и обязан упасть, затем пишется минимальная
реализация, затем тест прогоняется снова.

Отличие от оригинала — судьба временного теста. По умолчанию тест постоянный
и остаётся в репозитории. Временный допускается там, где постоянный держать
негде или незачем: разовый скрипт, проверка миграции, одноразовая сверка
данных. Правила для временного теста:

- он удаляется после запуска;
- его код целиком и его вывод целиком попадают в отчёт — это единственный
  след, который от него остаётся;
- выбор «временный» обосновывается в отчёте одной строкой;
- ревьюер вправе не согласиться с обоснованием и потребовать постоянный тест
  через обычный fix-loop.

Красный флаг, названный явно: тест, который ничего не утверждает, и тест,
написанный после реализации под её фактическое поведение.

## core/subagents.md

Порт `dispatching-parallel-agents` плюс правила составления промптов из
`subagent-driven-development`.

- Всё, что вставлено в промпт, и всё, что субагент напечатал в ответ,
  остаётся в контексте контроллера до конца сессии. Артефакты передаются
  путями к файлам, а не текстом.
- Промпт описывает одну задачу, а не историю сессии. Сводки прошлых задач в
  промпт не попадают.
- Субагент не порождает субагентов. Ревью приходит от контроллера, после
  отчёта.
- Несколько имплементеров параллельно не запускаются — они конфликтуют на
  файлах.
- Модель выбирается под роль: механическая задача на 1-2 файла — дешёвая,
  многофайловая интеграция — средняя, архитектура и финальное ревью — самая
  способная. Модель указывается явно при каждом диспетче.
- Ожидание запущенных субагентов: пока есть локальная работа — работать,
  простой — ждать ограниченными отрезками, между отрезками сверять список
  живых детей.

## core/feedback.md

Порт `receiving-code-review`. Замечание проверяется, а не выполняется
автоматически и не отвергается автоматически. Согласие без проверки и спор
без технического аргумента — обе формы одной ошибки.

## core/artifacts.md

Имена и расположение артефактов, формат ledger, формат отчёта имплементера.
Единственное место, где эти форматы описаны; режимы и промпты ссылаются сюда.

## Режимы

### modes/brainstorm.md

Порт `brainstorming`. Три пути — spike, bounded, architectural — сохраняются,
как и гейт: ни строчки реализации, пока пользователь не одобрил замысел.

Отличия:

- **на архитектурном пути перед спекой обязателен прогон через `grill-me`** —
  скил прожарки гипотез из этого же репозитория. Он задаёт по одному
  открытому вопросу, ищет нестыковки, неоднозначности, неизвестные и
  усложнения, и останавливается только по прямой команде пользователя.
  Спека не пишется, пока прожарка не проведена: её выходной документ в
  `docs/grill-me/<дата>-<тема>/` становится входом для спеки, а не
  пересказывается по памяти. Причина: вопросы брейншторма выясняют, что
  человек хочет; прожарка проверяет, выдерживает ли то, что он хочет,
  сопротивление. Это разные работы, и вторая до сих пор в наборе
  отсутствовала;
- шаг «закоммитить документ дизайна» удалён;
- спека сохраняется в `docs/kirpr-flow/specs/YYYY-MM-DD-<тема>-design.md`;
- самопроверка спеки идёт по формату «документ»: файл читается целиком, а не
  тем куском, что писался последним;
- визуальный компаньон из оригинала не портируется — он тянет за собой
  сервер и скрипты, а набор состоит только из markdown.

### modes/plan.md

Порт `writing-plans` с одним структурным изменением: план пишется каталогом,
а не одним файлом.

`00-overview.md` содержит цель, архитектуру, стек, путь к спеке и раздел
«Глобальные ограничения» — проектные требования, скопированные из спеки
дословно, с точными значениями.

`task-NN.md` содержит: список файлов (создать, изменить с указанием строк,
тесты), блок «Интерфейсы» (что задача потребляет от предыдущих и что
предоставляет следующим — с точными сигнатурами), и шаги по 2-5 минут с
чекбоксами.

Шаг «Commit» из шаблона задач удалён. Последним шагом задачи идёт
верификация в одном из четырёх форматов с указанием точной команды и
ожидаемого вывода. Режим прямо запрещает вписывать в план шаги с git —
имплементер обязан исполнять план дословно, и шаг «закоммить» в плане
означает либо нарушенный запрет, либо задачу, которую исполнитель не сможет
закрыть.

Запрет плейсхолдеров сохраняется целиком: «TBD», «добавить обработку
ошибок», «написать тесты для вышеописанного», «аналогично задаче N» — это
дефекты плана, а не сокращения.

Самопроверка плана — по формату «документ»: каждый файл плана читается
целиком, проверяются покрытие спеки, плейсхолдеры и согласованность имён и
типов между задачами.

### modes/execute.md

Порт `subagent-driven-development` — центральный режим. Описан отдельным
разделом ниже.

### modes/execute-inline.md

Порт `executing-plans`: исполнение в текущей сессии, без субагентов, с
контрольными точками. Отличия от оригинала: шаг «создать worktree» удалён,
финал ведёт в `modes/finish.md`, верификация каждой задачи обязана быть в
одном из четырёх форматов.

Режим остаётся вторым по предпочтительности: если субагенты доступны,
используется `execute`.

### modes/review.md

Порт `requesting-code-review`. Вместо диапазона SHA ревьюер получает список
файлов и читает их целиком. Заполняет `prompts/code-reviewer.md`.

Аргумент режима — либо путь к каталогу плана (список файлов собирается из
ledger), либо перечень путей через пробел. Если аргумента нет, режим
спрашивает, что ревьюить, и не угадывает: без git список изменённых файлов
взять неоткуда.

### modes/debug.md

Порт `systematic-debugging`. Сохраняются: запрет чинить до понимания причины,
трассировка до корня, защита в несколько слоёв, воспроизводящий тест до
исправления. Из порта убран пункт «посмотреть git diff и последние коммиты»
среди источников контекста — вместо него чтение затронутых файлов и отчётов
из `reports/`.

Исправление, найденное в режиме `debug`, верифицируется по общим правилам:
тест, воспроизводивший баг, должен упасть до исправления и пройти после.

### modes/finish.md

Замена `finishing-a-development-branch`. Git не трогает. Выдаёт:

1. Сводку сделанного: задачи, файлы, результаты верификации.
2. Полный список решений, принятых за пользователя (строки `Решение:` из
   ledger), в порядке принятия, каждое с ценой ошибки.
3. Список отложенных замечаний с их местом в коде.
4. Какие файлы созданы, изменены и удалены за работу — объединение секций
   «Файлы» из ledger. Не сканирование дерева: без git отличить свою правку от
   чужой нельзя, и сводка честно говорит, что она собрана из отчётов.
5. Что осталось несделанным и почему.

Никаких вариантов «слить, запушить, оставить» — это решения пользователя вне
набора.

### modes/skill.md

Порт `writing-skills`. Из него убран финальный чеклист-пункт «закоммитить
скил и запушить в форк». Тестирование скилов субагентами сохраняется — оно
не требует git.

## Цикл execute

### Подготовка

Изоляции нет. Проверок ветки нет — их нельзя сделать без git. Режим прямо
сообщает пользователю: работа идёт в текущем рабочем дереве, за его
состояние отвечает пользователь.

Дальше: прочитать `00-overview.md`, проверить наличие `progress.md`, создать
todo на каждую задачу.

Если `progress.md` существует и его первая строка называет этот план, задачи
со строкой `Задача N: готово` считаются сделанными — их не перезапускают,
работа продолжается с первой задачи без такой строки. Задача, последняя
строка которой — раунд правок, находится внутри fix-loop: продолжать со
следующего раунда. Ledger, первая строка которого называет другой план, —
чужой: не трогать, завести свой.

Первая строка ledger: `# kirpr-flow ledger — план: <путь к каталогу плана>`.

Перед первой задачей — разбор плана на противоречия. Строка на каждую пару
задач, делящих файл или интерфейс: что одна производит против того, что
другая потребляет. Строка на каждую задачу: согласован ли её текст сам с
собой. Таблица пишется в ledger. Найденное разрешается решением до старта,
каждое решение пишется в ledger.

### Контракт отчёта

```markdown
## Статус
DONE | DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED

## Файлы
Создано:  path/to/new.go — зачем он нужен
Изменено: path/to/old.go — что именно поменялось
Удалено:  path/to/dead.go — почему

## Верификация
Формат:  код | скрипт | БД | документ
Команда: <точная команда>
Вывод:   <вывод команды>

## Сомнения
```

Секция «Файлы» несущая: пропущенный в ней файл ревьюер не откроет, и
изменение уедет непроверенным. Это цена отказа от диффа.

Контроллер отклоняет отчёт без секции «Файлы» или без секции «Верификация»
до ревью — это не находка ревьюера, а невыполненный контракт. Отклонение
возвращается тому же имплементеру и не считается раундом fix-loop. Два
отклонения подряд по одной задаче означают, что имплементер не понял
контракт: дальше с задачей поступают так же, как если бы имплементер вернул
BLOCKED, — свежий имплементер на более сильной модели, с контрактом отчёта
дословно в промпте.

### Диспетч имплементера

Имплементер получает:

1. Одну строку о том, где эта задача в проекте.
2. Путь к `task-NN.md` с указанием: читать первым делом, это требования, все
   точные значения брать оттуда дословно.
3. Путь к своему файлу отчёта `reports/task-NN.md` и контракт отчёта.
4. Интерфейсы и решения предыдущих задач, которых файл задачи знать не может.
5. Раздел «Глобальные ограничения» из `00-overview.md`.
6. Выжимку правил из `core/rules.md` — дословным блоком, первой.

Не получает: историю сессии, сводки прошлых задач, файл плана целиком.

Если предыдущая задача отложила замечание в области, которой касается эта, —
в промпт кладётся указатель на строку ledger.

Мелкие однотипные правки, разбросанные по файлам, отдаются одним промптом
одному субагенту и ревьюятся как одна единица. Отдельный диспетч на задачу
оправдан там, где задаче нужны собственные тесты и собственная поверхность
ревью.

### Ревью задачи

Task-reviewer получает четыре пути: `task-NN.md`, `reports/task-NN.md`,
`00-overview.md` и список файлов из отчёта. Читает файлы целиком.

Даёт два вердикта: соответствие спеке (что требовалось — что сделано, что
сделано сверх) и качество задачи. Отчёт без обоих вердиктов не принимается.

Контроллер не судит за ревьюера заранее. Инструкции вида «не отмечай X»,
«максимум minor», «так решено планом» в промпт ревьюера не попадают: спорная
находка разрешается после ревью, а не подавляется до него.

Ревьюер вправе отметить пункты «не проверяется из предоставленного» —
требования, живущие в файлах, которых задача не касалась. Они не блокируют
ревью, но контроллер обязан разрешить каждый сам: подтверждённый пробел
входит в fix-loop наравне с находками.

### Правило бойскаута

Ревьюер читает файлы целиком и видит старый код рядом с новым. Найденное
чинится, но в границе: чинится всё в файлах, которых коснулась задача.
Проблема за их пределами уходит в ledger отложенной строкой и попадает в
финальное ревью, которое решает, что чинить до конца работы. Расширить
границу может контроллер — решением с записью в ledger.

### Fix-loop

Запускается на: несоответствие спеке, находку уровня Critical или Important,
подтверждённый контроллером пробел. Находки уровня Minor в цикл не входят —
они пишутся в ledger строкой `Задача N: minor (отложено): <одна строка>` и
передаются финальному ревью.

Пять раундов на задачу. Раунды 1-3 — возобновление того же имплементера с
дословным списком находок. Раунды 4-5 — свежий имплементер на более сильной
модели, с путями к задаче и отчёту и рамкой «предыдущий исполнитель пытался
N раз, теперь задача твоя, читай отчёт».

Каждый раунд: имплементер правит, перезапускает тесты, покрывающие изменённое,
дописывает отчёт о правках в тот же файл отчёта. Контроллер убеждается, что в
отчёте о правках есть покрывающие тесты, команда и вывод, и только тогда
запускает повторное ревью.

Повторное ревью узкое: получает список находок, файл задачи, файл отчёта и
файлы, которые правились в этом раунде. Выносит по каждой находке
«устранено» или «не устранено» и отмечает новые поломки в правках. Новые
Critical и Important из правок присоединяются к списку открытых находок.
Наблюдения не по теме уходят в ledger отложенными.

После каждого раунда — строка в ledger:
`Задача N: раунд правок R/5 (устранено X, открыто Y — <находки одной строкой>)`.

Контроллер не чинит сам: правки контроллера минуют ревью и загрязняют его
контекст.

### Предохранитель

Когда после пятого раунда находки открыты, диспетчи прекращаются. Контроллер
разбирает каждую открытую находку сам:

- ревьюер не прав или вопрос спорный — отложить строкой
  `Задача N: отложено — <находка> — Решение: <почему код остаётся>`;
- находка настоящая, но на ней ничего не строится — отложить так же, с
  пометкой, что она настоящая;
- находка настоящая и несущая (на ней строится следующая задача или она
  вскрывает дефект плана) — принять решение о наименьшем изменении, которое
  разблокирует зависимую работу, записать
  `Задача N: Решение: <находка> — <что решено и почему>` и передать это
  решение в промпт следующей задачи.

Разбор идёт только на пятом раунде. Разбор раньше — это подавление находок
под другим названием. Молчаливое отбрасывание находки запрещено.

### Завершение задачи

`Задача N: готово (файлы: a.go, b.go; верификация: <команда> — <итог>; ревью чисто)`
или `… ; отложено K` после сработавшего предохранителя. Затем todo
закрывается, работа идёт к следующей задаче.

### Финальное ревью

Получает объединение всех файлов из ledger, читает их целиком, плюс список
отложенных замечаний для сортировки. Запускается на самой способной
доступной модели.

Находки финального ревью отдаются одному субагенту одним списком, не по
исполнителю на находку. Затем ровно одно узкое повторное ревью правок.
Остаточные находки разбираются как на предохранителе: отложить с решением
или принять решение по несущим. Второй волны правок нет — остаточные несущие
находки выходят к пользователю через `modes/finish.md`.

### Остановки

Работа не останавливается между задачами ради вопросов «продолжать ли».
Конфликты, неоднозначности и дефекты плана разрешаются решением с записью в
ledger.

Останавливают четыре вещи: необратимая или разрушительная операция;
действие, затрагивающее безопасность; побочный эффект вне рабочего дерева, о
котором принято спрашивать; план, сломанный настолько, что любой путь вперёд
— догадка.

## Промпты субагентов

Шесть шаблонов. Каждый начинается с дословной выжимки правил из
`core/rules.md`.

| Файл | Кого запускает |
|---|---|
| `implementer.md` | Исполнитель задачи |
| `task-reviewer.md` | Ревьюер задачи: соответствие спеке + качество |
| `re-review.md` | Узкое повторное ревью раунда правок |
| `code-reviewer.md` | Широкое ревью по списку файлов |
| `spec-reviewer.md` | Проверка спеки перед планированием |
| `plan-reviewer.md` | Проверка плана перед исполнением |

В `implementer.md` два правила, которых нет в оригинале и которые возникли
из отсутствия отката: не трогать файлы вне своего списка и не переписывать
файл целиком там, где хватает точечной правки. Без коммитов испорченный файл
не возвращается штатными средствами.

Ревьюерские шаблоны получают список файлов вместо диапазона SHA и обязаны
читать файлы целиком, а не выборочно.

## Принятые риски

**Пропущенный файл в отчёте не проверяется.** Дифф ловил такое механически,
чтение по списку — нет. Смягчение: контракт отчёта обязателен, отчёт без
секции «Файлы» отклоняется, финальное ревью читает объединение всех файлов
за всю работу.

**Отката нет.** Испорченный файл восстанавливает пользователь своими
средствами. Смягчение: ограничение зоны правок в промпте имплементера.

**Ledger — единственная память.** Сверить его не с чем: истории коммитов
нет. Смягчение: запись в ledger идёт сразу после каждого шага, а не пачкой в
конце; ledger не удаляется по завершении работы.

**Чтение файлов целиком дороже диффа.** На большом плане финальное ревью
читает много. Смягчение: читает отдельный субагент с чистым контекстом, и он
последний в работе.

**Набор не активируется сам.** В отличие от superpowers с его
SessionStart-хуком, `kirpr-flow` вызывается явно. Это осознанный выбор:
хук конфликтовал бы с установленным плагином superpowers.

## Критерии приёмки

1. Ни одной git-команды в наборе. Проверяется в два шага:
   - `grep -rnE 'git (add|commit|checkout|branch|diff|log|status|push|pull|merge|stash|rebase|worktree|rev-parse|clean|init)' skills/kirpr-flow/`
     даёт совпадения только в `core/rules.md`, где перечисляются запрещённые
     команды. Совпадение в любом другом файле — протечка.
   - `grep -rn '\bgit\b' skills/kirpr-flow/` читается построчно: каждое
     совпадение обязано стоять в контексте запрета — перечень запрещённых
     команд, объяснение, чего набор не делает, или причина, по которой
     чего-то нельзя проверить. Совпадение в любом другом смысле — протечка.
     Перечнем файлов этот критерий не задаётся: слово попадает в каждый
     `prompts/*.md` через дословную выжимку правил и в те режимы, которым
     нужно объяснить границу, — а такой перечень расходится с набором при
     первой же правке.
2. Каждый файл набора прочитан целиком после написания и проверен по
   чеклисту: плейсхолдеры, внутренние противоречия, места с двумя
   прочтениями.
3. Все двенадцать скилов оригинала имеют соответствие в таблице
   «Соответствие оригиналу», и файл по каждому соответствию существует.
4. Сквозной прогон на игрушечной задаче: `plan` → `execute` → `finish`.
   Прогон идёт во временном каталоге вне репозитория, чтобы игрушечные
   артефакты не попали в `docs/kirpr-flow/`. Проверяется, что имплементер не
   выполняет git-команд, отчёт содержит обе обязательные секции, ревьюер
   читает файлы целиком, ledger позволяет продолжить работу после обрыва.
5. `install.sh` устанавливает `kirpr-flow` в `~/.claude/skills/kirpr-flow/`
   со всеми подкаталогами, `uninstall.sh` его удаляет. Проверяется
   исполнением: запуск установки, проверка наличия файлов, запуск удаления,
   проверка отсутствия.
6. README репозитория описывает `kirpr-flow` наравне с `expert-panel` и
   `grill-me`.

## За рамками

- Визуальный компаньон брейншторма (сервер и скрипты).
- Поддержка платформ, отличных от Claude Code (Codex, Pi, Antigravity,
  Hermes — ссылки на них из `using-superpowers` не портируются).
- Автоматическая активация через SessionStart-хук.
- Любая работа с системой контроля версий, включая подсказки пользователю о
  том, что и как коммитить.
