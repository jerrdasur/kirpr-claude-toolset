# Задача 6: modes/execute.md — исполнение субагентами

Центральный режим набора и самый большой файл. Порт
`subagent-driven-development` с заменой всей git-механики.

**Файлы:**
- Создать: `skills/kirpr-flow/modes/execute.md`

**Интерфейсы:**
- Потребляет: контракт отчёта и формат ledger из `core/artifacts.md`
  (задача 1); правила диспетчеризации из `core/subagents.md` (задача 3);
  шаблоны `prompts/implementer.md`, `prompts/task-reviewer.md`,
  `prompts/re-review.md` (задача 4) и `prompts/code-reviewer.md` (задача 5).
  Имена подстановок берутся из задач 4 и 5 дословно.
- Предоставляет: `modes/finish.md` (задача 9) вызывается отсюда последним
  шагом и читает ledger, который ведёт этот режим.

**Источник для портирования:** `SKILL.md` скила
`subagent-driven-development` из
`~/.claude/plugins/cache/claude-plugins-official/superpowers/6.3.0/skills/`.
Из оригинала выбрасываются: создание worktree, запись BASE через
`git rev-parse`, генерация review package, все упоминания коммитов в ledger,
удаление рабочего каталога в конце, переход в
`finishing-a-development-branch`.

- [ ] **Шаг 1: Создать `skills/kirpr-flow/modes/execute.md` — разделы 1-3**

**Раздел «Аргумент».** Путь к каталогу плана. Если аргумента нет — спросить,
какой план исполняем. Если по пути ничего нет или в нём нет
`00-overview.md` — сказать это и спросить.

**Раздел «Подготовка».** Порядок:

1. Сказать пользователю прямым текстом: изоляции нет, работа идёт в текущем
   рабочем дереве, за его состояние отвечает пользователь. Проверить
   состояние ветки набор не может — это git.
2. Прочитать `00-overview.md`, запомнить раздел «Глобальные ограничения».
3. Проверить наличие `progress.md` в каталоге плана.
4. Создать todo на каждую задачу.

Восстановление по ledger: если `progress.md` существует и его первая строка
называет этот план, задачи со строкой `Задача N: готово` считаются
сделанными — их не перезапускают, работа продолжается с первой задачи без
такой строки. Задача, последняя строка которой — раунд правок, находится
внутри цикла правок: продолжать со следующего раунда. Ledger, первая строка
которого называет другой план, — чужой: не трогать, завести свой.

Отдельным абзацем — почему это важно: ledger единственная память набора,
сверить его не с чем, история изменений нигде больше не хранится. После
сжатия контекста верить ledger, а не своим воспоминаниям.

Первая строка нового ledger:

```
# kirpr-flow ledger — план: <путь к каталогу плана>
```

**Раздел «Разбор плана до старта».** Перед первой задачей — поиск
противоречий. Результат — таблица, а не вердикт:

- строка на каждую пару задач, делящих файл или интерфейс: что одна
  производит против того, что другая потребляет;
- строка на каждую задачу: согласован ли её текст сам с собой — тесты,
  которые она задаёт, против кода, который она задаёт; файлы, которые она
  создаёт, против файлов, которые потом трогает.

Таблица пишется в ledger. Найденное разрешается решением до старта, каждое
решение пишется строкой `Задача N: Решение: …`. Формулировка «разбор чистый»
без строк таблицы разбором не считается.

- [ ] **Шаг 2: Дописать разделы 4-6 — цикл задачи**

**Раздел «Диспетч имплементера».** Что кладётся в промпт, нумерованным
списком:

1. Одна строка о том, где эта задача в проекте.
2. Путь к `task-NN.md` с пометкой «читать первым делом, это требования, все
   точные значения брать оттуда дословно».
3. Путь к файлу отчёта `reports/task-NN.md` и контракт отчёта.
4. Интерфейсы и решения предыдущих задач, которых файл задачи знать не может.
5. Раздел «Глобальные ограничения» из `00-overview.md`.
6. Блок выжимки правил — первым, до всего остального.

Что не кладётся: история сессии, сводки прошлых задач, файл плана целиком.

Отдельными строками: если предыдущая задача отложила замечание в области,
которой касается эта, — в промпт кладётся указатель на строку ledger; мелкие
однотипные правки, разбросанные по файлам, отдаются одним промптом одному
субагенту и ревьюятся как одна единица; несколько имплементеров параллельно
не запускаются.

Шаблон: `prompts/implementer.md`.

**Раздел «Приём отчёта».** Контроллер читает отчёт, а не файлы. Проверяет
наличие секций «Файлы» и «Верификация». Отчёт без любой из них отклоняется
до ревью — это невыполненный контракт, а не находка ревьюера. Отклонение
возвращается тому же имплементеру и раундом правок не считается. Два
отклонения подряд по одной задаче — дальше как при `BLOCKED`: свежий
имплементер на более сильной модели, с контрактом отчёта дословно в промпте.

Обработка четырёх статусов, по абзацу на каждый:

- `DONE` — переходим к ревью;
- `DONE_WITH_CONCERNS` — прочитать сомнения; если они про корректность или
  объём, разобраться до ревью; если это наблюдения, записать и идти дальше;
- `NEEDS_CONTEXT` — дать недостающее и перезапустить;
- `BLOCKED` — оценить причину: не хватает контекста (дать и перезапустить на
  той же модели), нужна большая способность (перезапустить на модели выше),
  задача велика (разбить), план неверен (принять решение, записать в ledger,
  перезапустить с решением в промпте). Никогда не перезапускать то же самое
  на той же модели без изменений.

**Раздел «Ревью задачи».** Ревьюер получает четыре пути: `task-NN.md`,
`reports/task-NN.md`, `00-overview.md` и список файлов из отчёта. Читает
файлы целиком. Отдаёт два вердикта — соответствие задаче и качество; отчёт
без обоих не принимается.

Запреты контроллеру, списком: не судить за ревьюера заранее — формулировки
«не отмечай X», «максимум minor», «так решено планом» в промпт не попадают;
не просить перезапускать тесты, уже прогнанные имплементером; не давать
открытых директив вроде «проверь все использования» без конкретной причины.

Пункты «не проверяется из предоставленного» разрешает контроллер сам:
подтверждённый пробел входит в цикл правок наравне с находками.

Шаблон: `prompts/task-reviewer.md`.

- [ ] **Шаг 3: Дописать разделы 7-9 — правила бойскаута, цикл правок, предохранитель**

**Раздел «Правило бойскаута».** Ревьюер видит старый код рядом с новым —
это ожидаемо. Найденное чинится в границе: все файлы, которых коснулась
задача. Проблема за их пределами уходит в ledger строкой
`Задача N: minor (отложено): …` и попадает в финальное ревью. Расширить
границу может контроллер — решением с записью в ledger.

**Раздел «Цикл правок».** Запускается на: несоответствие задаче, находку
`Critical` или `Important`, подтверждённый контроллером пробел. Находки
`Minor` в цикл не входят — пишутся в ledger отложенными и передаются
финальному ревью.

Пять раундов на задачу. Раунды 1-3 — возобновление того же имплементера с
дословным списком находок. Раунды 4-5 — свежий имплементер на более сильной
модели, с путями к задаче и отчёту и рамкой: «предыдущий исполнитель пытался
N раз, теперь задача твоя, читай отчёт».

Каждый раунд: имплементер правит и заново предъявляет доказательство того
формата, к которому относится задача, — прогон покрывающего теста для кода,
повторный запуск для скрипта, проверяющий запрос для БД, чтение целиком для
документа. Отчёт о правках дописывается в тот же файл отчёта. Контроллер
убеждается, что в отчёте о правках есть доказательство, команда и вывод, и
только тогда запускает повторное ревью.

Повторное ревью узкое: список находок, файл задачи, файл отчёта и файлы,
правившиеся в этом раунде. По каждой находке — «устранено» или «не
устранено». Новые `Critical` и `Important` из правок присоединяются к
открытым находкам. Наблюдения вне области уходят в ledger отложенными и
цикл не продлевают. Шаблон: `prompts/re-review.md`.

После каждого раунда — строка в ledger:

```
Задача N: раунд правок R/5 (устранено X, открыто Y — <находки одной строкой>)
```

Отдельной строкой: контроллер не чинит сам — его правки минуют ревью и
загрязняют контекст, который нужен для координации.

**Раздел «Предохранитель».** После пятого раунда с открытыми находками
диспетчи прекращаются. Контроллер разбирает каждую находку сам, три исхода:

- ревьюер не прав или вопрос спорный — отложить строкой
  `Задача N: отложено — <находка> — Решение: <почему код остаётся>`;
- находка настоящая, но на ней ничего не строится — отложить так же, с
  пометкой, что она настоящая;
- находка настоящая и несущая — принять решение о наименьшем изменении,
  которое разблокирует зависимую работу, записать
  `Задача N: Решение: <находка> — <что решено и почему>`, передать решение в
  промпт следующей задачи.

Разбор идёт только на пятом раунде. Разбор раньше — подавление находок под
другим названием. Молчаливое отбрасывание запрещено.

- [ ] **Шаг 4: Дописать разделы 10-14 — завершение, финальное ревью, остановки, финал, отговорки**

**Раздел «Завершение задачи».** Строка в ledger:

```
Задача N: готово (файлы: a.go, b.go; верификация: <команда> — <итог>; ревью чисто)
```

или, после сработавшего предохранителя:

```
Задача N: готово (файлы: a.go, b.go; верификация: <команда> — <итог>; отложено K)
```

Затем todo закрывается. Переходить к следующей задаче с открытыми
`Critical` или `Important`, которые не исправлены и не отложены с решением,
нельзя.

**Раздел «Финальное ревью».** Список файлов — объединение секций «Файлы» из
всех строк ledger. Ревьюер читает их целиком, получает список отложенных
замечаний для сортировки, запускается на самой способной доступной модели.
Шаблон: `prompts/code-reviewer.md`.

Находки финального ревью отдаются одному субагенту одним списком — не по
исполнителю на находку. Затем ровно одно узкое повторное ревью правок.
Остаточные находки разбираются как на предохранителе. Второй волны правок
нет: остаточные несущие находки выходят к пользователю через
`modes/finish.md`.

**Раздел «Остановки».** Работа не останавливается между задачами ради
вопросов «продолжать ли». Конфликты, неоднозначности и дефекты плана
разрешаются решением с записью в ledger.

Останавливают ровно четыре вещи: необратимая или разрушительная операция;
действие, затрагивающее безопасность; побочный эффект вне рабочего дерева, о
котором принято спрашивать; план, сломанный настолько, что любой путь вперёд
— догадка.

**Раздел «Финал».** Собрать из ledger все строки со словом `Решение:` и
передать их в `modes/finish.md`. Каталог плана не удалять: в этом наборе он
и есть запись о работе.

**Раздел «Отговорки».** Таблица «отговорка → что на самом деле», минимум
семь строк. Обязательно: «примерно соответствует задаче — сойдёт»; «сам
починю, диспетч дороже»; «ещё один раунд, и сойдётся»; «правка мелкая,
повторное ревью не нужно»; «находка очевидно ошибочная, выброшу»; «ledger —
лишняя бухгалтерия»; «имплементер сам запустил ревьюера, это плюс».
