# Задача 8: modes/brainstorm.md и modes/review.md

Вход в цикл и заказ ревью.

**Файлы:**
- Создать: `skills/kirpr-flow/modes/brainstorm.md`
- Создать: `skills/kirpr-flow/modes/review.md`

**Интерфейсы:**
- Потребляет: пути артефактов из `core/artifacts.md` (задача 1);
  `prompts/spec-reviewer.md` и `prompts/code-reviewer.md` (задача 5);
  `core/feedback.md` (задача 3).
- Предоставляет: `modes/plan.md` (задача 7) получает на вход спеку,
  созданную здесь, по пути
  `docs/kirpr-flow/specs/YYYY-MM-DD-<тема>-design.md`.

**Источник для портирования:** скилы `brainstorming` и
`requesting-code-review` из
`~/.claude/plugins/cache/claude-plugins-official/superpowers/6.3.0/skills/`.
Из `brainstorming` выбрасываются шаг коммита документа и весь визуальный
компаньон. Из `requesting-code-review` выбрасывается получение диапазона
SHA.

---

- [ ] **Шаг 1: Создать `skills/kirpr-flow/modes/brainstorm.md`**

Разделы:

**«Аргумент».** Тема свободным текстом или путь к файлу с формулировкой.
Нет аргумента — спросить, что разбираем, и не начинать без ответа.

**«Гейт».** До одобрения пользователем — ни строчки реализации, ни
scaffolding, ни вызова других режимов. Это правило действует на всех трёх
путях, включая самый мелкий. Объём документа меняется, гейт — нет.

**«Объявление пути».** Классификация называется вслух до первого вопроса,
одной строкой: какой путь выбран и почему. Причина, впиши её в текст: без
объявления пользователь узнаёт о классификации только по факту
предъявленного результата, когда работа уже идёт по выбранному пути.
Объявленную классификацию пользователь вправе оспорить сразу — и это самый
дешёвый момент её исправить. Тихая самоклассификация — способ пропустить
гейт, не нарушая ни одного другого правила.

**«Три пути».** По абзацу на каждый:

- *Разведка* — вопрос осуществимости, результат которого ответ, а не код.
  Изложить вопрос и способ проверки в двух-трёх предложениях, получить
  согласие, выяснить самым дешёвым способом, доложить рекомендацию. Всё
  построенное помечается как одноразовое.
- *Ограниченная задача* — правка кода, который в репозитории уже есть.
  Знание предметной области не считается: ограниченной задача становится,
  когда поток, который меняем, можно прочитать здесь и сейчас. Уточняющие
  вопросы, короткий дизайн в переписке, остановка до явного согласия.
- *Архитектурная* — новый проект, новая подсистема, изменение того, как
  части стыкуются. Полный процесс: вопросы, два-три подхода, дизайн по
  секциям с одобрением каждой, спека, самопроверка, чтение пользователем.

**«Правило сомнения».** При выборе между двумя путями берётся более тяжёлый.
Храповик односторонний: обнаруженная по ходу сложность поднимает путь вверх,
вниз не опускает ничего.

**«Объём секций дизайна».** Секция дизайна пишется по её сложности:
несколько предложений там, где всё прямолинейно, до двух-трёх абзацев там,
где есть тонкость. Раздутая секция про очевидное скрывает ту, где нужен
разбор. И отдельным правилом: резать лишнее беспощадно — возможность,
которой никто не просил, попавшая в дизайн, дальше попадёт в план и в
реализацию, где убирать её будет дороже всего.

**«Вопросы».** По одному за сообщение. Предпочтительно с вариантами.
Понимать цель, ограничения и признак успеха.

**«Прожарка перед спекой».** Только на архитектурном пути, обязательный шаг
перед написанием спеки. Тема прогоняется через скил `grill-me` из этого же
репозитория: `/grill-me <тема или путь к файлу с формулировкой>`. Он задаёт
по одному открытому вопросу, ищет нестыковки, неоднозначности, неизвестные и
усложнения, факты добывает субагентами и останавливается только по прямой
команде пользователя.

В разделе должно быть сказано:

- спека не пишется, пока прожарка не проведена. Это гейт, а не пожелание;
- выходной документ прожарки лежит в `docs/grill-me/<дата>-<тема>/` и
  становится входом для спеки: его читают целиком, а не пересказывают по
  памяти. Найденные там неизвестные и допущения переносятся в спеку как
  есть, разделённые по основанию — факт со ссылкой, ответ пользователя,
  допущение;
- зачем это нужно, одной фразой: вопросы брейншторма выясняют, чего человек
  хочет, а прожарка проверяет, выдерживает ли желаемое сопротивление. Две
  разные работы;
- что делать, если `grill-me` не установлен: сказать об этом прямо, назвать
  путь установки (`skills/grill-me/` в репозитории `claude-toolset`) и
  спросить пользователя, продолжать ли без прожарки. Молча пропускать шаг
  нельзя — это тот же обход гейта, что и тихая самоклассификация;
- если пользователь просит пропустить прожарку — пропустить, но записать это
  в спеку строкой «прожарка пропущена по решению пользователя», чтобы
  читатель спеки знал, какой глубины проверку она прошла.

**«Спека».** Сохраняется в
`docs/kirpr-flow/specs/YYYY-MM-DD-<тема>-design.md`. Не коммитится — это
git-операция; пользователь решает сам.

**«Самопроверка спеки».** Формат «документ»: прочитать файл целиком, а не
последний написанный кусок. Проверить плейсхолдеры, внутренние
противоречия, объём, неоднозначности. Найденное починить на месте. При
желании — запустить `prompts/spec-reviewer.md` отдельным агентом.

**«Гейт чтения».** Попросить пользователя прочитать спеку и сказать, что
менять. Дальше идти только после явного одобрения.

**«Дальше».** Режим `plan`. Никакой другой режим отсюда не вызывается.

**«Отговорки».** Таблица минимум из пяти строк. Обязательно: «это слишком
просто, чтобы согласовывать»; «назову задачу ограниченной и пропущу спеку»;
«дизайн очевиден, начну пока читают»; «я знаю такие приложения, значит
задача ограниченная»; «разведка сработала, оставлю код».

- [ ] **Шаг 2: Создать `skills/kirpr-flow/modes/review.md`**

Разделы:

**«Аргумент».** Либо путь к каталогу плана — тогда список файлов собирается
из ledger; либо перечень путей через пробел. Нет аргумента — спросить, что
ревьюить. Не угадывать: без git список изменённых файлов взять неоткуда.

**«Когда заказывать ревью».** Обязательно: после каждой задачи в режиме
`execute`; после крупной функциональности. Полезно: когда работа встала;
перед перестройкой существующего кода.

**«Как заказывать».** Заполнить `prompts/code-reviewer.md`: что построено,
требования, список файлов, отложенные замечания. Модель — по таблице из
`core/subagents.md`. Список файлов передаётся путями; содержимое файлов в
промпт не вставляется.

**«Почему субагент, а не сам».** Чтение диффа в своём контексте съедает
окно, нужное для координации. У субагента файлы и разбор живут в его
контексте, к вам возвращаются только находки.

**«Что делать с находками».** `Critical` — чинить сразу; `Important` —
чинить до перехода дальше; `Minor` — записать. Возражать, если ревьюер не
прав, по правилам из `core/feedback.md`: техническое основание и ссылка на
файл, а не «я считаю иначе».

- [ ] **Шаг 3: Верификация — формат «документ»**

Прочитать оба файла целиком:

```
Read skills/kirpr-flow/modes/brainstorm.md
Read skills/kirpr-flow/modes/review.md
```

Проверить и записать результат по каждому пункту:

1. В `modes/brainstorm.md` присутствуют все тринадцать разделов из шага 1,
   включая «Объявление пути», «Объём секций дизайна» и «Прожарка перед
   спекой»; таблица отговорок содержит минимум пять строк.
2. Путь сохранения спеки совпадает с `core/artifacts.md` — сверять чтением
   обоих файлов.
3. Визуальный компаньон нигде не упоминается.
4. В `modes/review.md` присутствуют все пять разделов из шага 2, и аргумент
   описан так же, как в `SKILL.md`.
5. Слово `git` встречается только в разделе «Спека» файла
   `modes/brainstorm.md` и в разделе «Аргумент» файла `modes/review.md` —
   оба раза как объяснение запрета. Ни одной git-команды.
6. Плейсхолдеров нет.
7. Гейт одобрения сформулирован так, что его нельзя прочитать как
   необязательный.

В отчёт: команды чтения, перечень проверенных разделов, результат по всем
семи пунктам.
