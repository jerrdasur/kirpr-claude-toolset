# Задача 2: SKILL.md — роутер

Точка входа набора. Разбирает аргумент, отправляет в режим, держит инвариант,
который действует везде.

**Файлы:**
- Создать: `skills/kirpr-flow/SKILL.md`

**Интерфейсы:**
- Потребляет: `core/rules.md` из задачи 1 — берёт оттуда выжимку правил и
  ссылается на файл за деталями.
- Предоставляет: имена восьми режимов и соответствие «имя режима → файл».
  Все задачи 6-9 создают файлы, перечисленные здесь; имена обязаны совпасть.

---

- [ ] **Шаг 1: Создать `skills/kirpr-flow/SKILL.md`**

Файл начинается с YAML-фронтматтера ровно такого вида (описание на русском,
как у `expert-panel` и `grill-me`):

```yaml
---
name: kirpr-flow
description: "Рабочий цикл разработки без единой git-операции: идея → спека → план → исполнение субагентами → ревью → финал. Верификация обязательна в одном из четырёх форматов. Вызывается явно: /kirpr-flow <режим> [аргумент]."
---
```

Дальше — пять разделов.

**Раздел «Что это».** Две-три строки: зонтичный скил, режимы вызываются
явно, ничего не запускается само.

**Раздел «Разбор аргументов».** Таблица соответствия:

| Начало строки | Файл режима |
|---|---|
| `brainstorm` | `modes/brainstorm.md` |
| `plan` | `modes/plan.md` |
| `execute` | `modes/execute.md` |
| `execute --inline` | `modes/execute-inline.md` |
| `review` | `modes/review.md` |
| `debug` | `modes/debug.md` |
| `finish` | `modes/finish.md` |
| `skill` | `modes/skill.md` |

Ниже таблицы — пять правил разбора:

- Сопоставление идёт по началу строки, а не по одному первому слову, и
  строка `execute --inline` проверяется раньше строки `execute`. Иначе
  двухтокенный режим недостижим: первое слово совпало бы с однотокенным
  `execute`, и `--inline` уехал бы в аргумент — пользователь получил бы
  исполнение субагентами вместо исполнения без них.
- Начало строки совпало с именем режима — читай соответствующий файл и
  следуй ему. Остаток строки, за вычетом распознанного имени режима, —
  аргумент.
- Ничего не совпало — спроси, какой режим нужен. Не угадывай.
- Аргументов нет — спроси, что делаем. Не угадывай по содержимому
  репозитория.
- Аргумент похож на путь, но по нему ничего нет — скажи это и спроси, что
  имелось в виду. Предметом такой аргумент не становится.

Отдельной строкой: пути к `core/*.md`, `modes/*.md` и `prompts/*.md` —
относительно каталога этого файла.

**Раздел «Инвариант».** Три пункта, действующие во всех режимах:

1. Git запрещён полностью — ни пишущих операций, ни читающих. Полный
   перечень в `core/rules.md`.
2. Верификация обязательна: код → тест, скрипт → запуск, БД → запрос,
   документ → чтение целиком. Доказательство — команда и её вывод.
3. Артефакты лежат по путям из `core/artifacts.md`.

**Раздел «Карта файлов».** Что где лежит и кто это читает: `core/` читают и
режим и субагент, `modes/` читает только режим, `prompts/` режим заполняет и
отдаёт субагенту.

**Раздел «Чего этот набор не делает».** Коротко, чтобы снять ожидания: не
коммитит, не создаёт веток и worktree, не предлагает слияние и публикацию,
не активируется сам без явного вызова.

- [ ] **Шаг 2: Верификация — формат «документ»**

Прочитать файл целиком:

```
Read skills/kirpr-flow/SKILL.md
```

Проверить и записать результат по каждому пункту:

1. Фронтматтер валиден: `name` и `description` на месте, `name` совпадает с
   именем каталога — `kirpr-flow`.
2. Все пять разделов присутствуют.
3. В таблице разбора ровно восемь строк, и каждое имя файла соответствует
   карте из `00-overview.md` этого плана. Правило сопоставления работает для
   двухтокенной строки `execute --inline`: проверь по тексту, что она
   распознаётся раньше однотокенной `execute`, иначе она недостижима.
4. Слово `git` встречается только в контексте запрета, и ни одна конкретная
   git-команда здесь не перечисляется — перечень живёт только в
   `core/rules.md`.
5. Плейсхолдеров нет.
6. Противоречий с `core/rules.md` нет: инвариант формулирует то же правило,
   что и файл правил, только короче.

В отчёт: команду чтения, перечень проверенных разделов, результат по всем
шести пунктам.
