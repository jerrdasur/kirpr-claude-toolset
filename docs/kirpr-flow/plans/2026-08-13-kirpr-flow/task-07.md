# Задача 7: modes/plan.md и modes/execute-inline.md

Планирование и запасной путь исполнения — без субагентов.

**Файлы:**
- Создать: `skills/kirpr-flow/modes/plan.md`
- Создать: `skills/kirpr-flow/modes/execute-inline.md`

**Интерфейсы:**
- Потребляет: пути артефактов из `core/artifacts.md` (задача 1);
  `prompts/plan-reviewer.md` (задача 5); `core/tests.md` (задача 3).
- Предоставляет: структуру каталога плана, которую читает `modes/execute.md`
  (задача 6): `00-overview.md` с разделом «Глобальные ограничения»,
  `task-NN.md` с блоком «Интерфейсы», `progress.md`, `reports/`.

**Источник для портирования:** скилы `writing-plans` и `executing-plans` из
`~/.claude/plugins/cache/claude-plugins-official/superpowers/6.3.0/skills/`.
Из `writing-plans` выбрасываются шаг «Commit» в шаблоне задачи и упоминание
worktree. Из `executing-plans` выбрасываются создание worktree и переход в
`finishing-a-development-branch`.

- [ ] **Шаг 1: Создать `skills/kirpr-flow/modes/plan.md`**

Разделы:

**«Аргумент».** Путь к спеке. Если аргумента нет — спросить, по какой спеке
планируем. Не угадывать по содержимому репозитория.

**«Проверка объёма».** Если спека покрывает несколько независимых
подсистем, предложить разбить на отдельные планы — по одному на подсистему.
Каждый план должен давать работающий и проверяемый результат сам по себе.

**«Карта файлов до задач».** Прежде чем резать на задачи, выписать, какие
файлы создаются и изменяются и за что каждый отвечает. Файлы с одной
ответственностью; файлы, меняющиеся вместе, лежат вместе; в существующей
кодовой базе следовать её образцам.

**«Размер задачи».** Задача — наименьшая единица, которая несёт собственный
цикл проверки и заслуживает отдельного ревью. Настройка, конфигурация и
документация складываются внутрь той задачи, чьему результату они нужны.
Резать там, где ревьюер мог бы осмысленно отклонить одну задачу, одобрив
соседнюю.

**«Структура каталога плана».** Блок в кодовой ограде:

```
docs/kirpr-flow/plans/YYYY-MM-DD-<тема>/
  00-overview.md
  task-01.md … task-NN.md
```

`progress.md` и `reports/` создаёт режим `execute`, планирование их не
трогает.

**«Что в 00-overview.md».** Цель одной строкой; архитектура в две-три
строки; стек; путь к спеке; раздел «Глобальные ограничения» — проектные
требования из спеки, скопированные дословно с точными значениями, по строке
на требование; карта файлов; порядок задач с объяснением, почему он такой.

**«Что в task-NN.md».** Блок «Файлы» (создать, изменить с указанием строк,
тесты); блок «Интерфейсы» — что задача потребляет от предыдущих и что
предоставляет следующим, с точными именами и сигнатурами, потому что
исполнитель видит только свою задачу; шаги по 2-5 минут с чекбоксами
`- [ ]`; последним шагом — верификация.

**«Верификация как последний шаг».** У каждой задачи последний шаг —
верификация в одном из четырёх форматов, с точной командой и ожидаемым
результатом. Формат выбирается по тому, что задача произвела: код → тест,
скрипт → запуск, БД → запрос, документ → чтение целиком.

**«Никакого git в плане».** Режим прямо запрещает вписывать в план шаги с
git-операциями. Исполнитель обязан следовать плану дословно, и шаг
«закоммитить» в плане означает либо нарушенный запрет, либо задачу, которую
исполнитель не сможет закрыть.

**«Запрет плейсхолдеров».** Списком, дефекты плана: «TBD», «доделать
позже», «добавить обработку ошибок», «добавить валидацию», «написать тесты
для вышеописанного» без самих тестов, «аналогично задаче N» вместо
повторения содержания, шаги без конкретики там, где нужен код, ссылки на
имена, не определённые ни в одной задаче.

**«Самопроверка».** Формат «документ»: прочитать каждый файл плана целиком и
проверить покрытие спеки, плейсхолдеры, согласованность имён и типов между
задачами. Найденное чинится на месте.

**«Проверка субагентом».** Опционально: заполнить
`prompts/plan-reviewer.md` и запустить проверку плана отдельным агентом.

**«Передача дальше».** Предложить два пути: `execute` — свежий субагент на
задачу с ревью между задачами, рекомендуемый; `execute --inline` — в текущей
сессии, если субагенты недоступны.

- [ ] **Шаг 2: Создать `skills/kirpr-flow/modes/execute-inline.md`**

Разделы:

**«Когда этот режим».** Только если субагенты недоступны. Если доступны —
`execute` лучше: свежий контекст на задачу и ревью между задачами.

**«Аргумент».** Путь к каталогу плана. Нет аргумента — спросить.

**«Порядок».**

1. Сказать пользователю: изоляции нет, работа идёт в текущем рабочем дереве,
   за его состояние отвечает пользователь.
2. Прочитать `00-overview.md` и все файлы задач.
3. Прочитать критически: выписать вопросы и сомнения к плану.
4. Если сомнения есть — поднять их с пользователем до начала работы.
5. Создать todo на каждую задачу.
6. Исполнять задачи по порядку: шаги дословно, верификация не пропускается.
7. Вести `progress.md` в том же формате, что `execute`.

**«Контрольные точки».** После каждой задачи — верификация и строка в
ledger. Пользователю показывается краткий итог, работа продолжается без
вопроса «продолжать ли».

**«Когда остановиться и спросить».** Два набора условий, оба обязательны.

Первый — общий для обоих режимов исполнения, скопировать из раздела
«Остановки» файла `modes/execute.md` дословно: необратимая или
разрушительная операция; действие, затрагивающее безопасность; побочный
эффект вне рабочего дерева, о котором принято спрашивать; план, сломанный
настолько, что любой путь вперёд — догадка. Причина, впиши её рядом: оба
режима работают в текущем рабочем дереве без изоляции, значит по риску
разрушительной операции они одинаковы, и защита у них обязана быть общей.
Хорошо описанный шаг «удалить каталог» не является ни блокером, ни пробелом
плана, ни падением верификации — без этого набора условий он просто
исполнится.

Второй — специфичный для исполнения без субагентов: блокер (недостающая
зависимость, падающая верификация, непонятная инструкция); критические
пробелы в плане, не дающие начать; верификация, падающая повторно. Эти три
компенсируют отсутствие эскалации через диспетч: в `execute` их закрывает
статус `BLOCKED` от имплементера, здесь возвращать статус некому.

Не продавливать блокер догадкой.

**«Финал».** Переход в `modes/finish.md`.

Прочитать оба файла целиком:

```

```

Проверить и записать результат по каждому пункту:

2. Структура каталога плана совпадает с `core/artifacts.md` — сверять
   чтением обоих файлов.
3. В шаблоне задачи нет шага «Commit», а раздел «Никакого git в плане»

4. В `modes/execute-inline.md` присутствуют все шесть разделов из шага 2,
   финал ведёт в `modes/finish.md`, а не в скил про завершение ветки.
5. Слово `git` встречается только в разделе «Никакого git в плане» файла
   `modes/plan.md`. Ни одной git-команды.
6. Плейсхолдеров нет.
7. Противоречий с задачей 6 нет: формат ledger и структура каталога плана
   описаны одинаково.

семи пунктам.
