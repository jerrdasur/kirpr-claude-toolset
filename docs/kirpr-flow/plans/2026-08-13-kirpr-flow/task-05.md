# Задача 5: промпты ревью артефактов

Три шаблона для проверок за пределами цикла задачи: широкое ревью кода,
проверка спеки и проверка плана.

**Файлы:**
- Создать: `skills/kirpr-flow/prompts/code-reviewer.md`
- Создать: `skills/kirpr-flow/prompts/spec-reviewer.md`
- Создать: `skills/kirpr-flow/prompts/plan-reviewer.md`

**Интерфейсы:**
- Потребляет: блок «Выжимка для промптов» из `core/rules.md` (задача 1) —
  копируется дословно в начало каждого файла.
- Предоставляет: `modes/review.md` (задача 8) заполняет
  `code-reviewer.md`; `modes/brainstorm.md` (задача 8) — `spec-reviewer.md`;
  `modes/plan.md` (задача 7) — `plan-reviewer.md`; `modes/execute.md`
  (задача 6) заполняет `code-reviewer.md` для финального ревью.

**Источник для портирования:** `code-reviewer.md` скила
`requesting-code-review`, `spec-document-reviewer-prompt.md` скила
`brainstorming`, `plan-document-reviewer-prompt.md` скила `writing-plans` —
все из
`~/.claude/plugins/cache/claude-plugins-official/superpowers/6.3.0/skills/`.

- [ ] **Шаг 1: Создать `skills/kirpr-flow/prompts/code-reviewer.md`**

Файл открывается блоком выжимки правил. Подстановки: `{ЧТО_ПОСТРОЕНО}`,
`{ТРЕБОВАНИЯ}`, `{СПИСОК_ФАЙЛОВ}`, `{ОТЛОЖЕННЫЕ_ЗАМЕЧАНИЯ}`.

Тело содержит:

**«Что ты получаешь».** Описание сделанного, требования, список файлов и
список отложенных замечаний, накопленных за работу.

**«Как читать».** Все файлы из `{СПИСОК_ФАЙЛОВ}` читаются целиком. Диффа
нет: предмет ревью — текущее состояние файлов.

**«Что искать».** Списком, минимум шесть пунктов: несоответствие
требованиям; ошибки корректности; дублирование логики; функциональность,
которой не просили; тесты, которые ничего не утверждают; места, где
изменения разных задач противоречат друг другу.

**«Сортировка отложенного».** По каждому пункту
`{ОТЛОЖЕННЫЕ_ЗАМЕЧАНИЯ}` — вердикт: чинить сейчас или оставить. Список,
который никто не разобрал, равнозначен молчаливо выброшенному.

**«Уровни находок».** Ссылка на шкалу в `../core/feedback.md`, раздел
«Калибровка находок». Критерии не пересказывать: пересказ разойдётся со
шкалой при первой же её правке. Так же, как это делают
`prompts/task-reviewer.md` и `prompts/re-review.md`.

**«Калибровка».** Отмечать то, что реально мешает: ошибку, дублирование,
несостыковку. Придирки к формулировкам и вкусовые предпочтения находками не
являются — иначе список находок обесценивается и его перестают читать.

**«Ты не запускаешь субагентов».** Ревью — конечная точка: результат уходит
контроллеру. Разбивать большой список файлов между помощниками нельзя;
если файлов много, читай их сам в несколько заходов.

**«Формат отчёта».** Находки по каждому пункту «Что искать», с указанием
файла и строки. Уровень по шкале. Отдельно — вердикт по каждому пункту
`{ОТЛОЖЕННЫЕ_ЗАМЕЧАНИЯ}`: чинить сейчас или оставить. Отдельно — список
советов, которые вердикт не блокируют: без этого разделения совет читается
как требование. Пункт «Что искать», неприменимый к предъявленному
материалу, отмечается строкой «неприменимо» с причиной, а не пропускается
молча.

**«Чего не делать».** Не менять файлы. Не выносить вердикт про слияние или
публикацию. Не запускать git-команды — их в этом наборе нет.

- [ ] **Шаг 2: Создать `skills/kirpr-flow/prompts/spec-reviewer.md`**

Файл открывается блоком выжимки правил. Подстановки: `{ПУТЬ_К_СПЕКЕ}`,
`{ИСХОДНАЯ_ЗАДАЧА}`.

Тело содержит:

**«Что делать».** Прочитать спеку целиком. Не куски, не по заголовкам.

**«Четыре проверки».** По каждой — свой раздел в отчёте:

1. Плейсхолдеры: «TBD», «уточнить позже», незаполненные разделы, требования
   без конкретных значений.
2. Внутренние противоречия: раздел против раздела, архитектура против
   описания возможностей, критерии приёмки против ограничений.
3. Неоднозначности: требования, которые можно прочитать двумя способами.
   По каждому — оба прочтения, чтобы автор выбрал.
4. Объём: хватит ли одной реализации, или спеку надо делить на части.

**«Калибровка».** Отмечать то, что помешает планированию: пробел,
противоречие, требование с двумя прочтениями. Придирки к формулировкам
находками не являются.

**«Ты не запускаешь субагентов».** Проверка спеки — конечная точка,
результат уходит тому, кто спеку писал.

**«Формат отчёта».** По каждой из четырёх проверок — список находок с
цитатой и номером строки, либо строка «находок нет». Отдельно — список
советов, которые вердикт не блокируют. Общий вердикт: готова к планированию
или нет.

- [ ] **Шаг 3: Создать `skills/kirpr-flow/prompts/plan-reviewer.md`**

Файл открывается блоком выжимки правил. Подстановки: `{ПУТЬ_К_ПЛАНУ}`,
`{ПУТЬ_К_СПЕКЕ}`.

Тело содержит:

**«Что делать».** Прочитать целиком все файлы каталога плана —
`00-overview.md` и каждый `task-NN.md` — и спеку.

**«Четыре проверки».**

1. Покрытие спеки: по каждому требованию спеки назвать задачу, которая его
   реализует. Требование без задачи — пробел.
2. Плейсхолдеры: «добавить обработку ошибок», «написать тесты для
   вышеописанного», «аналогично задаче N», шаги без конкретики.
3. Согласованность имён и типов: имя, введённое в одной задаче, совпадает с
   именем, используемым в другой.
4. Наличие верификации: у каждой задачи последним шагом стоит верификация в
   одном из четырёх форматов, с точной командой.

**«Отдельная проверка на git».** В плане не должно быть ни одного шага с
git-операцией. Найденный шаг «закоммитить» — дефект уровня `Critical`:
исполнитель обязан следовать плану дословно и получит шаг, который не имеет
права выполнить.

**«Калибровка».** Отмечать то, что помешает исполнению: пробел в покрытии,
плейсхолдер, расхождение имён, отсутствующая верификация. Придирки к
формулировкам находками не являются.

**«Ты не запускаешь субагентов».** Проверка плана — конечная точка,
результат уходит тому, кто план писал.

**«Формат отчёта».** По каждой проверке — список находок либо «находок нет».
Отдельно — список советов, которые вердикт не блокируют. Общий вердикт:
готов к исполнению или нет.

- [ ] **Шаг 4: Верификация — формат «документ»**

Прочитать все три файла целиком:

```
Read skills/kirpr-flow/prompts/code-reviewer.md
Read skills/kirpr-flow/prompts/spec-reviewer.md
Read skills/kirpr-flow/prompts/plan-reviewer.md
```

Проверить и записать результат по каждому пункту:

1. Каждый файл начинается с блока выжимки правил, посимвольно совпадающего
   с `core/rules.md`. Сверять чтением обоих файлов.
2. Подстановки записаны в том же виде, что в этой задаче: `{ЧТО_ПОСТРОЕНО}`,
   `{ТРЕБОВАНИЯ}`, `{СПИСОК_ФАЙЛОВ}`, `{ОТЛОЖЕННЫЕ_ЗАМЕЧАНИЯ}`,
   `{ПУТЬ_К_СПЕКЕ}`, `{ИСХОДНАЯ_ЗАДАЧА}`, `{ПУТЬ_К_ПЛАНУ}`.
3. В `code-reviewer.md` раздел «Что искать» содержит минимум шесть пунктов.
4. В `spec-reviewer.md` и `plan-reviewer.md` по четыре проверки, и каждая
   имеет описанный формат вывода.
5. Слово `git` встречается только внутри блока выжимки правил и в разделе
   «Отдельная проверка на git» файла `plan-reviewer.md`.
6. Плейсхолдеров нет.

В отчёт: команды чтения, перечень проверенных разделов, результат по всем
шести пунктам.
