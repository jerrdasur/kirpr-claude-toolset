# task-create / task-update / task-delete — CRUD по одиночной задаче

**Дата:** 2026-07-25
**Статус:** дизайн утверждён

## Задача

В репозитории есть чтение задачи (`fetch_youtrack.py`, `fetch_jira.py`) и пакетное создание подзадач из декомпозиции (`create_youtrack.py` + `/kirpr:tasks-push`). Точечных операций по одной задаче нет: нельзя создать одиночную задачу, изменить поля существующей или удалить её.

Нужно вернуть три операции — create, update, delete — по одной задаче, по запросу на естественном языке, для обоих трекеров.

## Решения

### Два независимых скрипта, а не общий слой

`manage_youtrack.py` и `manage_jira.py` самодостаточны. Общего модуля, общего клиента и общего CLI нет.

Причина: API и возможности трекеров расходятся слишком сильно. В YouTrack поля меняются командным языком (`State In Progress`), в Jira статус идёт через transitions API, assignee требует резолва `accountId`, а произвольных полей вне фиксированного набора нет. Общий интерфейс поверх этого был бы либо ложью, либо наименьшим общим знаменателем.

Это согласуется с тем, как уже устроен репозиторий: `fetch_youtrack.py` и `fetch_jira.py` — тоже два независимых файла с продублированным HTTP-обвесом.

Цена решения принята осознанно: скелет (транспорт, клиент, рендер, `run`, `main`) дублируется в двух файлах.

### Скрипты плоские, без подкаталогов

`install.sh` копирует `kirpr/scripts/*.py` глобом. Подкаталог его сломает.

### Delete — жёсткое удаление

`DELETE /api/issues/{id}` в YouTrack, `DELETE /rest/api/2/issue/{key}` в Jira. Задача исчезает вместе с комментариями, связями и историей. Отката нет.

Защита двухрубежная: промпт команды требует ввести номер задачи вручную (`да` не принимается), скрипт независимо требует `--confirm`, совпадающий с номером.

### Jira REST v2

Не v3. В v2 описание — обычная строка, а не ADF. `fetch_jira.py` уже на v2.

### Изоляция от декомпозиции

Новые команды не читают и не пишут `create-plan.json` и `.created.json`, не используют `create_youtrack.py`. `/kirpr:tasks-push` остаётся пакетным путём для декомпозиции, новые команды — точечным для одиночных задач.

## CLI

### manage_youtrack.py

```
manage_youtrack.py [--dry-run] create --project SAS --summary "..."
                   [--description "..." | --description-file f]
                   [--parent SAS-200] [--command "assignee ivanov"]... [--comment "..."]

manage_youtrack.py [--dry-run] update SAS-201 [--summary "..."]
                   [--description "..." | --description-file f]
                   [--command "State In Progress"]... [--comment "..."]

manage_youtrack.py [--dry-run] delete SAS-201 [--confirm SAS-201]
```

`--command` повторяемый и покрывает все поля: `State`, `assignee`, `Priority`, `tag`, спринты. Отдельных флагов под каждое поле нет — они были бы обёрткой над той же строкой.

`--description` и `--description-file` взаимоисключающие.

**Резолв проекта при создании.** `GET /api/admin/projects?fields=id,shortName` → найти по `shortName`. Если запрос недоступен (нет прав) и задан `--parent` — взять проект из родительской задачи через `GET /api/issues/{parent}?fields=project(id,shortName)`. Если оба пути не сработали — ошибка с объяснением, что нужен либо доступ к списку проектов, либо `--parent`.

**Порядок операций при create:** создать задачу (`POST /api/issues`) → применить `--command` → проставить `subtask of {parent}` при наличии `--parent` → добавить комментарий.

**Порядок операций при update:** `POST /api/issues/{id}` с `summary`/`description` → `POST /api/commands` по одной на каждый `--command` → комментарий.

### manage_jira.py

```
manage_jira.py [--dry-run] create --project PROJ --summary "..." --type Task
               [--description "..." | --description-file f]
               [--parent PROJ-200] [--status "..."] [--assignee ...] [--priority ...]
               [--labels a,b] [--comment "..."]

manage_jira.py [--dry-run] update PROJ-201 [--summary "..."]
               [--description "..." | --description-file f]
               [--status "In Progress"] [--assignee ivanov] [--priority Major]
               [--labels a,b] [--duedate 2026-08-01] [--comment "..."]

manage_jira.py [--dry-run] delete PROJ-201 [--confirm PROJ-201] [--delete-subtasks]
```

Поддерживаемые поля — ровно перечисленные. Других нет: произвольные кастомные поля вне области задачи.

**`--type`** обязателен при создании: issue type — обязательное поле Jira.

**`--status`** идёт не через запись поля: `GET /rest/api/2/issue/{key}/transitions` → найти переход, у которого `to.name` совпадает с запрошенным статусом (сравнение без учёта регистра) → `POST` этот переход. Перехода нет — ошибка со списком доступных целевых статусов.

**`--assignee`** зависит от развёртывания. Cloud определяется по наличию `JIRA_EMAIL` — та же эвристика, что уже используется в `fetch_jira.py` для выбора схемы авторизации.
- Cloud: `GET /rest/api/2/user/search?query={value}` → взять `accountId` → `{"assignee": {"accountId": ...}}`. Ноль совпадений или больше одного — ошибка с перечислением найденного.
- Server: `{"assignee": {"name": value}}`.
- Значение `-1` снимает исполнителя.

**`--labels`** — список через запятую, заменяет текущий набор целиком (не добавляет).

**`--parent`** пишется в `fields.parent`. Работает для subtask-типов и для дочерних задач в team-managed проектах. Если API отказал — показать ответ как есть, без попыток угадать причину.

**Порядок операций при create:** `POST /rest/api/2/issue` (project, summary, description, issuetype, parent, priority, labels) → transition при `--status` → комментарий.

**Порядок операций при update:** `PUT /rest/api/2/issue/{key}` с полями → transition при `--status` → комментарий.

**Delete:** `DELETE /rest/api/2/issue/{key}?deleteSubtasks=true|false`. Без `--delete-subtasks` — `false`; если у задачи есть подзадачи, Jira вернёт ошибку, и скрипт покажет её вместе с подсказкой про флаг.

## Устройство скрипта

Один скелет в обоих файлах:

- `_urllib_transport(method, url, headers, data)` — возвращает `(status, body)`, не бросает на HTTP-ошибках. Копия подхода из `create_youtrack.py`.
- Класс клиента (`YouTrackClient` / `JiraClient`) с инъекцией `transport=` — тесты обходятся без сети.
- `render_dry_run(...)`, `render_report(...)` — чистые функции: принимают данные, возвращают строку.
- `run(...)` — оркестрация, принимает `client=` для подмены.
- `main(argv=None)` — argparse и коды возврата.

Границы те же, что в `create_youtrack.py`.

## Предпросмотр

`--dry-run` перед `update` и `delete` делает один GET текущего состояния — иначе «было» неоткуда взять. Перед `create` состояния ещё нет: печатается карточка будущей задачи, но проект всё равно резолвится (GET), чтобы опечатка в `--project` вскрылась до подтверждения, а не после.

Описание — построчный diff через `difflib`, не два полотна текста.

**Ограничение YouTrack.** `--command` — строка на командном языке, её результат до выполнения неизвестен. Поэтому в предпросмотре YouTrack колонка «станет» есть только у `summary`, а команды перечисляются отдельным списком без предсказания результата. Обещать точный результат там, где его нельзя вычислить, нельзя.

```
# Dry-run: обновление SAS-201

**Задача:** Починить экспорт отчётов

| поле | было | станет |
|------|------|--------|
| summary | Починить экспорт отчётов | Починить экспорт отчётов в CSV |

## Описание

  Экспорт падает на больших выборках.
- Воспроизводится начиная с 10к строк.
+ Воспроизводится начиная с 5к строк.
+ Причина — таймаут на стороне БД.

## Команды

- `State In Progress`
- `assignee ivanov`

_dry-run: сетевых записей не выполнено._
```

В Jira поля типизированы, поэтому «станет» показывается для всех:

```
# Dry-run: обновление PROJ-201

**Задача:** Починить экспорт отчётов

| поле | было | станет |
|------|------|--------|
| status | Open | In Progress |
| assignee | — | ivanov |
| priority | Major | Critical |

_dry-run: сетевых записей не выполнено._
```

Предпросмотр перед delete печатает `summary`, автора, число комментариев, связи и подзадачи — чтобы было видно, что именно исчезнет. `--confirm` при `--dry-run` не требуется: предпросмотр — это то, что показывают человеку **до** того, как он вводит номер.

## Частичный отказ

Запись не атомарна. Если операция упала на середине — скрипт печатает, что уже применено и что нет, и выходит с ненулевым кодом.

Откат не делается: он мог бы затереть чужую параллельную правку. Повторный запуск той же команды безопасен — все операции, кроме создания задачи и добавления комментария, идемпотентны по значению.

## Ошибки

HTTP-статус и тело ответа попадают в текст ошибки, как в `create_youtrack.py`. Частые случаи разбираются отдельно:

- 401 / 403 — «проверь токен и права».
- 404 на задаче — «задача не найдена».
- 400 на transitions (Jira) — список доступных переходов.

Все ошибки в stderr, код возврата ненулевой.

## Slash-команды

Каждая команда — тонкий промпт. Логика в скриптах.

**Общая инициализация:** прочитать `~/.claude/kirpr/config/tracker.md`, секция `## Активный трекер` → выбрать `manage_youtrack.py` или `manage_jira.py`. Трекер не настроен — сообщить и остановиться.

### /kirpr:task-create

Аргумент свободный: `SAS Починить экспорт` или «заведи в SAS задачу про таймауты в экспорте». Команда достаёт проект, формулирует `summary` и `description`, недостающее спрашивает по одному вопросу за раз. Для Jira дополнительно уточняет `--type`, если он не очевиден из запроса.

Dry-run → «Создать задачу в проекте SAS? да/нет» → создание → номер и ссылка.

### /kirpr:task-update

Читает текущее состояние задачи через `--dry-run`, раскладывает запрос на естественном языке в флаги, показывает таблицу `поле: было → станет` и просит подтверждение. Правку описания показывает как diff.

### /kirpr:task-delete

Печатает `summary`, автора, число комментариев, связи и подзадачи. Требует ввести номер задачи вручную — `да` не принимается — и передаёт его в `--confirm`. У Jira при наличии подзадач отдельно спрашивает про каскад. Предупреждает, что откатить нельзя.

### Правила во всех трёх

Как в `tasks-push`: один вопрос за раз, без подтверждения не писать, при ошибке скрипта показать её и остановиться.

## Тесты

`tests/test_manage_youtrack.py`, `tests/test_manage_jira.py` — `unittest` с подменённым транспортом, как в `tests/test_create_youtrack.py`.

Покрываем:

- `update` без единого изменяющего флага — ошибка, а не пустой запрос к API.
- `delete` без `--confirm` или с несовпадающим номером — отказ.
- `--description` вместе с `--description-file` — ошибка.
- `--dry-run` не делает ни одного пишущего запроса: проверка по журналу вызовов фейкового транспорта, только `GET`.
- `render_dry_run` / `render_report` на фикстурах — без клиента.
- Diff описания: пустое описание, замена, добавление строк.
- YouTrack: резолв проекта через список проектов и фолбэк через `--parent`.
- YouTrack: `--command` попадает в `POST /api/commands` без искажений; в предпросмотре — без колонки «станет».
- Jira: `--status` находит переход по имени целевого статуса; перехода нет — ошибка со списком доступных.
- Jira: `--assignee` в Cloud (есть `JIRA_EMAIL`) резолвит `accountId`, в Server отправляет `name`; ноль или несколько совпадений — ошибка.
- Частичный отказ: вторая операция вернула 400 — отчёт перечисляет применённое, код возврата ненулевой.

## Установка и документация

- `install-remote.sh` — пять новых строк: три команды и два скрипта. Список там явный.
- `install.sh` — правок не требует: копирует команды и скрипты глобом.
- `uninstall.sh` — правок не требует: сносит каталоги целиком.
- `README.md` — новая секция «Работа с задачами» с тремя командами; `task-fetch` переезжает туда из «Декомпозиции задач», потому что тоже про одиночную задачу. Явная строка о необратимости `task-delete`.

## Non-goals

- Массовые операции над несколькими задачами одним вызовом.
- Управление связями между задачами. `--parent` при создании — единственное исключение.
- Вложения, work items, учёт времени.
- Произвольные кастомные поля Jira за пределами перечисленного набора.
- Кэш и офлайн-режим.
