# Дизайн: создание задач в YouTrack с зависимостями (`/kirpr:tasks-push`)

> Дата: 2026-07-01
> Статус: одобрен, готов к написанию плана реализации

## Проблема

В toolset `kirpr` есть слой чтения из трекера (`fetch_youtrack.py` + команды
`/kirpr:task-fetch`, `/kirpr:tasks-decompose`). Декомпозиция производит директорию
`sas-200/` с графом зависимостей и файлами подзадач, но обратного пути нет: чтобы
завести эти подзадачи в YouTrack с иерархией и зависимостями, приходится делать это
вручную.

Нужен «обратный» аналог fetch: инструмент, который берёт готовую декомпозицию и
создаёт из неё задачи в YouTrack, проставляя связи. Это замыкает цикл
**fetch → decompose → push**.

## Решения (зафиксированы с пользователем)

| Вопрос | Решение |
|--------|---------|
| Источник задач | Директория декомпозиции `sas-200/` (`00-overview.md` + `XX-Y-name.md`) |
| Типы связей | Иерархия (`Subtask` от родителя) **+** зависимости (`Depend` из графа) |
| Поля задач | Только `Summary` + `Description` (минимум) |
| Идемпотентность | Маппинг-файл `.created.json` + обязательный `--dry-run` preview |
| Трекер | Только YouTrack (Jira — будущее расширение, вне scope) |

## Архитектура

Тот же двухслойный паттерн, что и у fetch, в обратную сторону:

```
sas-200/ (декомпозиция)
   │  LLM-слой: /kirpr:tasks-push читает 00-overview.md + XX-Y-name.md
   ▼
create-plan.json  ──►  create_youtrack.py  ──►  YouTrack API
   (tasks[] + edges[])      (тупой, stdlib)      (создание + связи)
                                   │
                                   ▼
                            sas-200/.created.json  (файл→ID, идемпотентность)
```

- **LLM (команда)** понимает декомпозицию: маппит файлы подзадач в задачи, извлекает
  граф зависимостей, строит план, делает preview, запрашивает подтверждение.
- **Скрипт (Python, stdlib)** детерминированный: принимает JSON-план, создаёт задачи,
  проставляет связи, ведёт маппинг-файл, поддерживает `--dry-run`. Никакого LLM,
  никакого парсинга прозы.

**Отвергнутая альтернатива:** скрипт сам парсит markdown-директорию. Хрупко (разбор
прозы) и нарушает принцип «тупого детерминированного скрипта» — fetch не парсит прозу,
а ходит в API. Промежуточный JSON-контракт даёт чистое разделение слоёв.

## Компонент 1 — скрипт `kirpr/scripts/create_youtrack.py`

Зеркалит стиль `fetch_youtrack.py`: только stdlib (`urllib`), env-переменные
`YOUTRACK_URL` / `YOUTRACK_TOKEN`, аккуратные ошибки в stderr, exit-коды.

**Интерфейс:**
```
python3 scripts/create_youtrack.py --plan sas-200/create-plan.json [--dry-run]
```

**Алгоритм (двухпроходный — иначе зависимости не проставить):**

1. **Валидация плана.** Структура JSON; все `edges` ссылаются на существующие `key`;
   граф ацикличен (топосорт). Ошибка → stderr, exit 1.
2. **Резолв проекта.** Из `parent` (`SAS-200`) запросить
   `GET /api/issues/SAS-200?fields=project(id,shortName)` → внутренний `project.id`.
   Проект не хардкодится.
3. **Загрузка маппинга.** Если рядом с планом есть `.created.json` — прочитать. Задачи
   с уже известным ID **пропускаются при создании** (идемпотентность).
4. **Проход 1 — создание задач.** Для каждой новой задачи `POST /api/issues` с
   `project.id`, `summary`, `description`. Запомнить `key → idReadable`. После каждого
   успешного создания — **инкрементально писать `.created.json`** (сбой на середине не
   приводит к дублям при повторе).
5. **Проход 2 — связи.** Когда у всех задач есть реальные ID:
   - **Иерархия:** каждая новая задача ← `Subtask` от `parent`.
   - **Зависимости:** для каждого ребра графа — `Depend`-связь.
   Идемпотентно: перед добавлением проверять существующие links задачи, дубли не
   создавать.
6. **Вывод.** Markdown-отчёт: таблица `файл → ID → ссылка`, список связей, итог.

**`--dry-run`:** шаги 1–3, затем печать «что было бы создано / какие связи», **без**
сетевых записей. Используется командой для preview.

**Технический риск — механизм связей.** У YouTrack несколько путей: commands API
(`POST /api/commands`, `query: "subtask of SAS-200"`) vs. links REST
(`POST /api/issues/{id}/links`). Точную рабочую форму и локализованные имена типов
связей (`Depend`/`Subtask`) проверить на реальном инстансе **первым делом** на этапе
реализации. `fetch_youtrack.py` уже читает `linkType(name)` и `direction` — брать имена
типов оттуда как опору.

## Компонент 2 — команда `commands/kirpr/tasks-push.md`

По стилю ближе к `tasks-decompose` (фазовый, с подтверждениями), но короче. Аргумент —
номер задачи (`SAS-200`).

**Фазы:**

1. **Загрузка контекста.** Прочитать `~/.claude/kirpr/config/tracker.md` (убедиться, что
   активный трекер = YouTrack; иначе сообщить, что push пока только для YouTrack).
   Проверить, что директория `sas-200/` существует. Прочитать `00-overview.md` и все
   `XX-Y-name.md`.
2. **Построение плана.** Собрать `create-plan.json`:
   - `tasks[]` — по одному на файл подзадачи: `key` (имя файла без расширения),
     `summary` (из заголовка `## Задача X.Y — {Название}`), `description` (тело файла).
   - `edges[]` — из ASCII-графа зависимостей в `00-overview.md`.
   - `parent` — `SAS-200`.
3. **Preview (dry-run).** Записать `create-plan.json`, запустить скрипт с `--dry-run`,
   показать таблицу создаваемых задач и связей. **Явно показать граф** для сверки.
4. **Подтверждение (гейт).** Спросить «Создаю N задач в проекте SAS?». Без явного «да»
   реальное создание не запускать — это необратимое outward-facing действие.
5. **Создание.** Запустить скрипт без `--dry-run`. При ошибке — показать stderr,
   остановиться (маппинг-файл частично записан, повторный запуск дозакроет).
6. **Отчёт.** Показать вывод скрипта: ID со ссылками, связи, итог. Упомянуть, что
   `.created.json` записан и повторный вызов идемпотентен.

**Правила** (в духе остальных команд): показывай план перед записью; не создавай задачи
без подтверждения; если fetch/резолв проекта упал — прерви.

## Контракт `create-plan.json`

```json
{
  "tracker": "youtrack",
  "parent": "SAS-200",
  "tasks": [
    {
      "key": "01-schema",
      "summary": "Схема БД для аудита",
      "description": "## Задача 1.1 — Схема БД...\n\n### 1. ...\n\nКритерий готовности: ..."
    },
    { "key": "02-1-domain-model", "summary": "...", "description": "..." }
  ],
  "edges": [
    { "from": "01-schema", "to": "02-1-domain-model" }
  ]
}
```

- `key` — стабильный идентификатор (имя файла), связывает `tasks`, `edges`,
  `.created.json`.
- `edges[].from → to` = «`from` раньше `to`» → `Depend`-связь. Точное направление
  зафиксировать в реализации после проверки на инстансе.
- `.created.json`: `{ "01-schema": "SAS-201", "02-1-domain-model": "SAS-202" }`.

## Крайние случаи

- **Циклы в графе** → падение на валидации (шаг 1), задачи не создаются.
- **Частичный сбой** в проходе 1 → `.created.json` записан инкрементально, повтор
  досоздаёт недостающее и проставляет связи.
- **Ребро на несуществующий `key`** → ошибка валидации.
- **Активный трекер не YouTrack** → команда сообщает, что push поддерживает только
  YouTrack.
- **`.created.json` и `create-plan.json`** — кэш-артефакты, добавить в `.gitignore`
  (как `.context.md`).

## Интеграция

- `install.sh` / `uninstall.sh` — убедиться, что `create_youtrack.py` копируется вместе
  с остальными скриптами, а `tasks-push.md` — из `commands/kirpr/`.
- README — строка в таблице «Декомпозиция задач»:
  `/kirpr:tasks-push SAS-200 — создаёт подзадачи в YouTrack с иерархией и зависимостями`.
- Тесты: скрипт проверяется через `--dry-run` на фейковом плане без сети; реальное
  создание — вручную на тестовом проекте YouTrack.

## Вне scope (YAGNI)

Jira-вариант; поля Estimation / Assignee / наследование от родителя; обновление уже
созданных задач; удаление / откат созданного.
