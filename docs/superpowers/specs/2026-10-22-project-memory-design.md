# kirpr: память проекта и уроки

**Дата:** 2026-10-22
**Статус:** дизайн утверждён
**Контекст:** сравнение kirpr с vmkteam-developer и независимый ресёрч решений памяти (проект «personal claude toolset», `claude/kirpr-vs-vmkteam-notes.md`, `claude/project-memory-research.md`).

## Задача

Скилы kirpr не помнят проект между вызовами: каждая декомпозиция заново исследует архитектуру, конвенции, генераторы и базовые ветки, а уроки прошлых задач (что пошло не так в декомпозиции или ревью) не накапливаются. У vmkteam-developer это решено через `project-index.md` с секцией «Уроки», но в auto-memory Claude Code — вне git, вне команды, вне Codex.

Нужна память на двух уровнях: рабочее пространство (карта сервисов) и репозиторий (как проверять, ловушки, уроки). Память должна одинаково работать в Claude Code и Codex, лежать в git и не требовать внешних сервисов.

## Сознательно принятые решения

- **Markdown в git, читаемый скилом явно.** Не auto-memory харнесса (не переносится, не видна команде), не AGENTS.md как хранилище (у Codex общий бюджет 32 KiB; по исследованию ETH контекст-файлы с обзорами архитектуры не повышают успех и удорожают работу на ~20 %).
- **Все записи через детерминированный скрипт, дельтами.** Модель не переписывает файл памяти целиком: по ACE полная перезапись сжимает контекст (18 282 → 122 токена) и роняет точность ниже «без памяти».
- **Запись уроков только с подтверждением человека.** Автозапись — главный канал отравления памяти; у vmkteam подтверждения нет.
- **Не хранить выводимое из кода.** В память идут только нестандартные практики, команды проверки, соответствия и уроки. Обзоры архитектуры, списки пакетов, пути, которые находятся grep-ом, — нет.
- **Эмбеддинги не делаем.** Память уместится в тысячи токенов; чтение целиком даёт полный recall. Путь на потом, если память и `docs/` перестанут помещаться: сначала ripgrep/FTS5 по `docs/`, затем опционально `fastembed` с мультиязычной моделью (bge-m3) и `sqlite-vec`, индекс в `.kirpr/cache/` под `.gitignore`.
- **Имя файла `memory.md`, не `project.md`** — чтобы не путать с проектом в трекере.

## Файлы и форматы

### `<workspace>/.kirpr/workspace.md`

Рабочее пространство — каталог, из которого запускается `tasks-decompose` (там же каталоги `sas-200/`). Одна таблица сервисов и строка о последнем обновлении.

```markdown
# Рабочее пространство: topscan

| Сервис | Путь | Базовая ветка | Трекер | Роль |
|---|---|---|---|---|
| scansrv | ../scansrv | devel | SAS | сканирование, RPC |
| upload-callback | ../upload-callback | main | SAS | CLI, poststop |

Обновлено скриптом: 2026-10-22 (`kirpr_memory.py refresh`)
```

Колонки «Сервис», «Путь», «Базовая ветка», «Трекер» собирает скрипт; «Роль» дописывает человек или модель с подтверждением.

### `<repo>/.kirpr/memory.md`

Три секции, порядок фиксирован.

```markdown
# Память: scansrv

## Как проверять
- `make test` — тесты с БД `scansrv_test`; `make lint`

## Ловушки
- `*_zenrpc.go` генерируется `make generate` после правки аннотаций; не ревьюить построчно

## Уроки
- [L-003] шаг декомпозиции ссылался на `Jobs().Summary`, в коде `Jobs().Info` → сверять сигнатуры RPC с кодом до записи задачи (SAS-200; 2026-10-22; refs: pkg/rpc/scan.go)
```

Формат урока: `- [L-NNN] что пошло не так → как избежать (TASK-ID; YYYY-MM-DD; refs: путь[, путь])`. `refs` необязателен. Урок — ошибка процесса декомпозиции или ревью, а не факт о коде.

Бюджет: 150 строк и 15 КБ на файл. Не хранится: обзор архитектуры, список пакетов, пути, находимые grep-ом, секреты.

Если `workspace.md` или `memory.md` нет — скилы работают как сейчас и один раз предлагают `kirpr-onboard`.

## Скрипт `kirpr/scripts/kirpr_memory.py`

Единственная точка записи в файлы памяти. Stdlib, без зависимостей. Все команды принимают `--dry-run`; вывод — plain text для показа пользователю. Запись — во временный файл и атомарный rename.

| Команда | Что делает |
|---|---|
| `refresh [--workspace DIR]` | Обходит соседние каталоги с `.git`: имя, относительный путь, default branch из `origin/HEAD` (fallback — текущая ветка), трекер — префикс вида `SAS-123` из последних коммитов. Сохраняет «Роль», базовую ветку и ручные строки; при первом запуске статусов нет, дальше новые сервисы помечает `новый`, пропавшие — `не найден`, не удаляет |
| `lesson add --file F --text T --task ID [--refs a,b]` | Следующий `L-NNN`; строка вставляется в конец «Уроков», остальной текст файла не меняется; итоговый файл проходит `lint`, иначе запись отменяется; дубль по нормализованному тексту или пересечению `refs` → печатает «похоже на L-003 — уточните его: `lesson amend L-003`», код выхода 2 |
| `lesson amend L-NNN --file F --text T` | Заменяет текст урока, обновляет дату. Полной перезаписи секции как операции нет |
| `lint --file F` | Бюджет строк и байт, регулярка формата урока, уникальность id, наличие и порядок секций |
| `role --workspace DIR --service S --role R` | Задаёт «Роль» сервиса в таблице; единственный способ записать роль |
| `init --file F --name N [--check L]... [--traps L]...` | Создаёт `memory.md` из шаблона; отказывается, если файл есть |
| `stale --file F` | Для каждого `refs` проверяет существование пути в репозитории, помечает `⚠ stale` в выводе; файл не меняет |

Шаблоны `workspace.md.template` и `memory.md.template` лежат в `kirpr/config/`, скрипт читает их при создании файлов.

## Чтение памяти в скилах

Правило загрузки — одно на три скила, в `templates.md`, секция «Loading decomposition context».

- **`tasks-decompose`**, Фаза 1 (`workflow.md`): до фетча прочитать `.kirpr/workspace.md`; нет — одна строка «карта рабочего пространства не найдена, запустите `kirpr-onboard`» и работа как сейчас. После фетча, когда известны сервисы на пути сценария, — `.kirpr/memory.md` каждого из них по путям из таблицы. Уроки учитываются в Фазе 2 и Фазе 5: перед чеклистом — проверка «ни одна задача не повторяет ситуацию из урока». «Как проверять» подставляется в списки «Проверить» вместо придуманных команд.
- **`tasks-review`**: Фаза 1 читает `memory.md` затронутых сервисов; пятая категория проверки «Уроки: задача не повторяет L-NNN», находка — `Важно` со ссылкой на id.
- **`tasks-adapt`**: читает память только для сервисов из зоны влияния.
- **`.context.md`** получает пункт «версия памяти» — дата из `workspace.md`, чтобы `review` видел, что память обновилась после декомпозиции.
- **`expert-panel`** не трогается: передача памяти агентам — решение подпроекта калибровки.

## Запись уроков (HITL)

Триггеры:
- `tasks-review`, после Фазы 5: были находки категорий «Противоречия» или «Пробелы» с расхождением с кодом, либо файл остался со score < 8.
- `tasks-adapt`, после Фазы E: пользователь выбрал «изменились требования» или «изменилось решение», и правка вызвана ошибкой декомпозиции, а не новым вводом.

Скил формулирует 0–3 кандидата в формате урока, запускает `lesson add --dry-run` на каждый (скрипт находит дубли и предлагает `amend`) и показывает результат как дифф: «добавить L-004 в `scansrv/.kirpr/memory.md`», «уточнить L-002». Запись — после явного «да» по каждому файлу; «нет» — ничего не пишется и не переспрашивается.

## Скил `kirpr-onboard`

Двенадцатый скил, явный вызов, `allow_implicit_invocation: false`, адаптер `/kirpr:onboard`.

1. `refresh --dry-run` — показать таблицу сервисов, спросить роли по одному.
2. Для каждого сервиса без `memory.md`: скрипт извлекает кандидатов «Как проверять» из `Makefile`, `go.mod`, CI-файла; модель задаёт не больше трёх вопросов на сервис про ловушки (генераторы, что не ревьюить, порядок генерации).
3. Показать оба файла целиком, записать после «да», напомнить закоммитить.

Повторный вызов — только дельта: новые сервисы и пустые секции. Опроса про инфраструктуру нет: у kirpr нет скилов, которым она нужна.

## Установщик, тесты, документация

- `installer/lib.sh`: `kirpr_memory.py` в `KIRPR_SCRIPTS`; `kirpr-onboard` в `KIRPR_SKILLS`; `onboard` в `KIRPR_COMMANDS`; оба шаблона в `KIRPR_CONFIG_FILES`. `uninstall.sh` убирает по манифесту.
- `tests/test_kirpr_memory.py`: `refresh` на временном рабочем пространстве из двух git-репозиториев, сохранение ручных строк и ролей, `lesson add` с дублем (код 2), `amend`, `lint` на бюджете и битом формате, `stale` на удалённом пути, атомарность записи.
- `tests/test_skill_contracts.py`: `kirpr-onboard` в `ALL_SKILLS`, адаптер ≤ 12 строк.
- `tests/test_kirpr_config_consistency.py`: секция загрузки упоминает `workspace.md` и `memory.md`; фазы `kirpr-onboard` существуют.
- `tests/test_documentation.py`: README документирует `/kirpr:onboard` и `$kirpr-onboard`.
- README: раздел «Память проекта» — где лежат файлы, что хранится и что нет, команды скрипта. `templates.md`: шаблоны обоих файлов, формат урока, правило содержания.

## Вне границ

Эмбеддинги и FTS-индекс; память в промптах `expert-panel`; синхронизация уроков с трекером; AGENTS.md как хранилище; автозапись без подтверждения; опрос про инфраструктуру.
