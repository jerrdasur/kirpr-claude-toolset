# expert-panel — скил мульти-персонного ревью

**Дата:** 2026-07-24
**Статус:** дизайн утверждён

## Задача

Панель экспертов (Пайк, Чейни, Форд, Стоунбрейкер) используется вручную — промпт живёт в голове и переписывается заново каждый раз. Нужно оформить её как самодостаточный скил Claude Code, который можно отдать другому человеку.

Два сценария применения:

1. **Ревью спеки** — критический разбор design-документа перед переходом к `writing-plans`, с последующим обновлением спеки.
2. **Ревью diff** — разбор изменений перед коммитом или MR.

## Ограничения

- **Только Go.** Чеклисты персон заточены под Go-сервисы: слои, error handling, конкурентность, миграции. Не пытаемся быть языко-агностичными.
- **Самодостаточность.** Папка скила не зависит от `~/.claude/kirpr/`. Скопировал папку — работает.
- **Скил, не команда.** Никаких `/kirpr:*`-обёрток.
- **Кастомизация переживает обновление.** Пользователь добавляет своих экспертов, переустановка их не стирает.

## Раскладка

```
skills/expert-panel/          → ~/.claude/skills/expert-panel/
  SKILL.md                    роутер, реестр ядра, severity, протокол синтеза
  experts/pike.md
  experts/cheney.md
  experts/ford.md
  experts/stonebraker.md
  custom-experts.md           overlay: пользовательские эксперты и отключение ядерных
  modes/spec.md               протокол ревью спеки
  modes/diff.md               протокол ревью git diff
```

`SKILL.md` определяет режим по аргументу и подгружает нужный файл из `modes/`. Файлы персон в контекст оркестратора не попадают — их читают агенты. Третий режим добавляется новым файлом в `modes/`, без правки `SKILL.md`.

## Панель

### Ядро

| Эксперт | Домен | Чем давит |
|---|---|---|
| Rob Pike | простота | преждевременные абстракции, лишние интерфейсы, «умный» код, неидиоматичный Go |
| Dave Cheney | границы | направление зависимостей, поверхность API пакета, error handling, конкурентность |
| Neal Ford | trade-offs | обратимость решения, blast radius, характеристики архитектуры, эволюционируемость |
| Michael Stonebraker | данные | модель и схема, выбор хранилища, консистентность и транзакции, стоимость запросов, миграции |

### Формат файла персоны

```
Цитата → Кто → Как ревьюит → Характерные вопросы
→ Что проверяет в спеке
→ Что проверяет в diff
```

Два чеклиста вместо одного, потому что режимы требуют разного. Стоунбрейкер в спеке спрашивает «почему вообще Postgres», в diff — «этот запрос сделает seq scan на 10M строк».

### Overlay

`custom-experts.md` — единственный файл, который установщик не перезаписывает. Формат секций тот же, что у ядра. Директива `disable:` отключает ядерного эксперта.

```markdown
disable: stonebraker

## Filippo Valsorda — Security
> "Every input is hostile until proven otherwise."
...
```

Активная панель = ядро − `disable:` + секции overlay.

## Исполнение

Оркестратор собирает активную панель и запускает по агенту на каждого эксперта параллельно. Агенту передаются: путь к файлу персоны, артефакт (спека или diff), список релевантных путей, read-only доступ к репозиторию.

Агент возвращает замечания в фиксированной схеме:

```
severity | место (раздел спеки или file:line) | суть | почему это проблема | что конкретно изменить
```

**Замечание без предложенной правки не принимается.** «Тут неясно» — не замечание. «В разделе X не описано поведение при Y; добавить абзац» — замечание.

Оркестратор дедуплицирует совпадения и выносит расхождения между экспертами отдельным блоком «Конфликты» — их разрешает пользователь. Пример конфликта: Пайк требует убрать слой абстракции, Форд настаивает сохранить ради обратимости решения.

### Severity

| | В спеке | В diff |
|---|---|---|
| `blocker` | ведёт к переделке: неверная модель данных, невыполнимое требование, противоречие | баг, уязвимость, потеря данных |
| `major` | существенный пробел: не описан отказ, миграция, граница ответственности | архитектурная проблема, неверная логика |
| `minor` | уточнение, экономящее вопросы на этапе плана | улучшение, некритично |
| `nit` | формулировка | стиль, нейминг |

Лимиты после дедупа: 3 `blocker`, 5 `major`, остальное по усмотрению. Отчёт должен быть про решения, а не про объём.

## Режим spec

Вызов: `/expert-panel spec <path>`. Без аргумента — свежий файл из `docs/superpowers/specs/`, при неоднозначности спрашивает.

**Фаза 1. Контекст.** Читает спеку, `CLAUDE.md` репозитория, находит затронутый код по ключевым терминам спеки. Показывает summary: тема спеки, задетые пакеты и сервисы, что из упомянутого в коде не найдено. Переход к фазе 2 — только по подтверждению пользователя.

**Фаза 2. Панель.** Параллельные агенты по протоколу выше.

**Фаза 3. Синтез и отчёт.** Дедуп, нумерация с префиксом эксперта (`P1`, `C2`, `F1`, `S3`), сортировка по severity, блок конфликтов.

**Фаза 4. Разбор.** Пользователь отвечает одной строкой: `accept 1,3,5; reject 2 — причина; ? 4`. Помеченные `?` обсуждаются по одному. Поштучный опрос по каждому замечанию дороже самого ревью — при 15 замечаниях это 15 раундов.

**Фаза 5. Правки.** Применяются только принятые, точечными правками. Спека не переписывается целиком. Показывается diff.

**Фаза 6. Журнал.** В конец спеки дописывается секция:

```markdown
## Review log

### 2026-07-24 — expert-panel (Pike, Cheney, Ford, Stonebraker)
Принято: C2 — добавлено поведение при недоступности X; S1 — схема переведена на …
Отклонено: F3 — вынос в отдельный сервис. Причина: преждевременно, объём не оправдан.
```

Отклонённые с причиной важнее принятых: при повторном прогоне панель читает журнал, не поднимает закрытые вопросы заново и отмечает, что из прошлых замечаний исправлено.

Коммит не делается. `writing-plans` не вызывается автоматически — скил сообщает, что спека готова к переходу.

## Режим diff

Вызов: `/expert-panel diff` — рабочее дерево против `HEAD`. `/expert-panel diff <base>` — против ветки.

**Preflight.** Проверка, что это git-репозиторий. При явной базе — `git fetch` и проверка отставания локальной базы от `origin`. Отстала — пауза и вопрос: обновить или ревьюить против устаревшей базы. Молча ревьюить неверный diff хуже, чем не ревьюить вовсе.

**Пропуск сгенерированного кода** — три слоя:

1. Go-стандарт: файлы с `// Code generated ... DO NOT EDIT.` в первой строке.
2. Дефолтный список: `vendor/`, `*.pb.go`, `*_mock.go`, `testdata/`.
3. Опциональный `.claude/expert-panel-ignore` в репозитории проекта. Набор генераторов — свойство проекта, а не скила: у vmkteam это `*_zenrpc.go` и `*_colgen.go`, у другой команды другое.

**Ревью.** Ревьюится только diff, контекст файла читается целиком. Каждое замечание — с `file:line`. Эксперты обязаны отмечать удачные решения, а не только проблемы: отчёт из одних претензий перестают читать.

**Связка со спекой.** `/expert-panel diff --spec <path>` добавляет проверку «код против спеки»: что из спеки не реализовано, что сделано сверх неё, какие решения из Review log нарушены.

**Разбор и правки** — по протоколу фаз 4–5 режима spec. Ограничение: скил правит код, но не запускает тесты и линтеры — выводит команды для запуска. Панель судит о коде, а не отвечает за то, что он собирается.

**Вердикт:** `Approve` / `Approve with comments` / `Request changes` с перечнем блокеров.

## Установка и распространение

| Файл | Изменение |
|---|---|
| `skills/expert-panel/**` | новое: `SKILL.md`, 4 персоны, 2 режима, шаблон `custom-experts.md` |
| `install.sh` | копирование `skills/` в `~/.claude/skills/`; бэкап и восстановление `custom-experts.md` по схеме, уже работающей для `tracker.md` |
| `install-remote.sh` | то же плюс скачивание файлов скила |
| `uninstall.sh` | удаление `~/.claude/skills/expert-panel/` с предложением сохранить `custom-experts.md` |
| `README.md` | раздел про скил, обновление структуры проекта |

Имя скила — `expert-panel`, без префикса `kirpr`: он не завязан на `~/.claude/kirpr/`.

### Попутный фикс

`install-remote.sh` не скачивает четыре файла, добавленных после его последнего обновления:

- `commands/kirpr/tasks-push.md`
- `commands/kirpr/text.md`
- `kirpr/prompts/text.md`
- `kirpr/scripts/create_youtrack.py`

Кто ставится «из интернета», получает 7 команд из 9, а `/kirpr:tasks-push` падает на отсутствующем скрипте. Дефект бьёт ровно в распространение — чиним здесь же.

## Что не делаем

- Не пишем автотесты на скил: это markdown, проверять нечем. Питоновские тесты в `tests/` не трогаем.
- Не лезем в трекер. Контекст задачи в скил не подтягивается — самодостаточность важнее.
- Не переносим `/kirpr:adr-review` на панель. Форд там уже прописан отдельно; объединение — возможный третий режим, но не в этой работе.
- Не делаем автотриггер по фразе вместо явного вызова: ревью с параллельными агентами слишком дорого запускать самопроизвольно.

## Изменения

### 2026-10-22 — калибровка по опыту vmkteam `/go-review`

- **Отменён лимит** «3 `blocker`, 5 `major` полностью, остальное — «Ниже порога»». Все находки показываются полностью. Причина: свёрнутый в одну строку `blocker` легко пропустить, а vmkteam пришёл к тому же после опыта («пропущенный баг дороже лишнего замечания»). Отчёт остаётся про решения за счёт калибровки severity, а не за счёт отсечения.
- **Схема находки:** поле `уверенность`; в режиме diff у `blocker`/`major` — `инвариант`, `ломающий вход`, `тест`. Правило «при сомнении — выше» заменено на «сомнение — в уверенности».
- **Valsorda в ядре** (префикс `V`), overlay с именем эксперта ядра заменяет его персону.
- **Критерии приёмки** проверяет оркестратор (Phase 1.5, префикс `A`), а не каждый агент; `--spec` принимает и файл задачи декомпозиции `NN-service.md`.
- **Генерёнка:** исключается из ревью, но устаревшая генерёнка — находка.
- Пункт «Не пишем автотесты на скил» больше не действует: контракты скила закреплены в `tests/test_skill_contracts.py`.
