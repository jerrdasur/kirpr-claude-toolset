# Критический review декомпозиции $ARGUMENTS

Ты — критический ревьюер декомпозиции. Твоя задача — найти все неоднозначности, противоречия, пропуски и риски в существующей декомпозиции, обсудить каждую находку с пользователем и исправить файлы.

## Инициализация

1. Прочитай файл `~/.claude/kirpr/config/templates.md` — там шаблоны, чеклисты, правила и паттерн загрузки контекста.
2. Разбери `$ARGUMENTS`:
   - Если передан только номер задачи (например `SAS-200`) → **review всей декомпозиции**.
   - Если передан номер + имя файла (например `SAS-200 02-1-domain-model.md`) → **review конкретной подзадачи**.
3. Найди директорию задачи (lowercase номер задачи).
4. Если директория не найдена — **прерви выполнение**: "Декомпозиция для {номер} не найдена. Используйте `/kirpr:tasks-decompose {номер}` для создания."

## Загрузка контекста

Следуй паттерну загрузки из `~/.claude/kirpr/config/templates.md` (секция «Загрузка контекста декомпозиции»).

После загрузки базового контекста:
- Если scope = вся декомпозиция → прочитай **все** файлы подзадач.
- Если scope = один файл → прочитай указанный файл + файлы, от которых он зависит (из графа).

## Выполнение

### Фаза 1: Исследование кодовой базы

Используй `.context.md` секция 2 как отправную точку. Дополнительно:
1. Для каждой подзадачи в scope — извлеки упомянутые **пути к файлам, пакеты, функции, SQL-таблицы**.
2. Проверь в кодовой базе:
   - Существуют ли указанные пути и пакеты?
   - Совпадают ли структуры данных (Go structs, SQL schemas) с описанием?
   - Совпадают ли конвенции (именование функций, паттерны тестов)?
   - Есть ли конфликты с уже существующим кодом?
3. Запомни все расхождения — они понадобятся в Фазе 2.

### Фаза 2: Анализ по 4 категориям

Проверь каждую подзадачу в scope по всем 4 категориям. Для каждой находки определи severity.

#### Категория 1: Неоднозначности
- [ ] Формулировки конкретные, не расплывчатые ("добавить логику", "обработать данные" — плохо)
- [ ] Все термины определены или ссылаются на основную задачу
- [ ] Критерии готовности проверяемые ("компиляция проходит, тесты зелёные" — хорошо; "всё работает" — плохо)
- [ ] Scope каждой подзадачи однозначен — разработчик не может трактовать по-разному
- [ ] Код-примеры полны (нет "и т.д.", "аналогично" без конкретики)

#### Категория 2: Противоречия
- [ ] Нет конфликтов между подзадачами (одна не отменяет другую)
- [ ] Граф зависимостей в `00-overview.md` соответствует тексту подзадач
- [ ] Нет дублирования работы между подзадачами
- [ ] Описанные пути, структуры, API совместимы с реальной кодовой базой
- [ ] Параллельные потоки действительно независимы

#### Категория 3: Пропуски/пробелы
- [ ] Для каждого функционального кода есть задача на тесты
- [ ] Если меняется схема БД — есть задача на миграции
- [ ] Edge cases из описания трекера покрыты в подзадачах
- [ ] Интеграции между сервисами/модулями учтены
- [ ] Задачи на документацию (ADR, API docs) не пропущены
- [ ] Error handling и rollback-сценарии описаны

#### Категория 4: Оценки и риски
- [ ] Все подзадачи <= 4 часов (иначе нужно дробить)
- [ ] Подозрительно мелкие подзадачи (< 1ч) — возможно, их стоит объединить
- [ ] Технические риски идентифицированы (новые зависимости, unfamiliar API, нет прототипа)
- [ ] Зависимости от внешних компонентов / других команд явно указаны
- [ ] Нет bottleneck в графе (одна задача не блокирует всё остальное)
- [ ] Оценки реалистичны с учётом сложности

### Фаза 2.5: Quality Scoring

Оцени каждую подзадачу в scope по рубрике из `~/.claude/kirpr/config/templates.md` (секция «Рубрика Quality Scoring»). Для каждого файла выстави баллы К1-К5 (0-2 каждый).

Покажи пользователю таблицу scores:

```
Оценка качества декомпозиции {номер}
Общий score: {X.X}/10

| Файл | К1 | К2 | К3 | К4 | К5 | Score | Главная проблема |
|------|----|----|----|----|----|-------|-----------------|
| 02-3-rpc-endpoints.md | 1 | 1 | 0 | 2 | 1 | 5 | К3: нет критерия готовности |
| 04-4-merge-sql.md | 2 | 1 | 1 | 1 | 2 | 7 | К2: не хватает SQL-примера |
| 03-1-feed-listing.md | 2 | 2 | 2 | 2 | 1 | 9 | ✅ ok |
| ... | | | | | | | |

Файлы со score >= 8: {N} из {M}
Файлы, требующие доработки (score < 8): {K}
```

### Фаза 3: Сводный отчёт

Покажи пользователю структурированный отчёт, **включая scores**:

```
Review декомпозиции {номер}
Scope: {вся декомпозиция / конкретный файл}
Проверено: {N} подзадач
Общий score: {X.X}/10

Критично ({K}):
  ❌ [02-1-domain-model.md] (score: 5) Путь `pkg/sast/policy.go` не существует в кодовой базе
  ❌ [03-2-issue-history.md] (score: 6) Нет задачи на тесты для issue history

Важно ({M}):
  ⚠️ [02-3-rpc-endpoints.md] (score: 7) Формулировка "добавить валидацию" неоднозначна — какие правила?
  ⚠️ [00-overview.md] Задача 4.2 зависит от 4.1, но в графе связь не показана

Замечания ({L}):
  💡 [04-4-merge-sql.md] (score: 7) Оценка 4ч — на границе, возможно стоит разбить
  💡 [05-1-recalc-cron.md] (score: 8) Нет описания rollback-сценария при ошибке
```

Спроси: "Начинаю итерацию по файлам с score < 8, от худшего к лучшему. Готовы?"

### Фаза 3.5: Итерационный цикл по качеству

Для каждого файла с score < 8, начиная с наихудшего:

1. **Покажи breakdown** — 5 критериев с баллами и объяснением, что не так в каждом.
2. **Предложи исправления** — конкретные изменения для поднятия слабых критериев.
3. **Дождись решения пользователя** — принять / отклонить / уточнить.
4. **Пересчитай score** — после принятия исправлений покажи новый score файла.
5. **Если score < 8** — предложи дополнительные улучшения (второй проход).
6. **Если score >= 8** — перейди к следующему файлу.

**Ограничение: max 2 итерации на файл.** Если после 2 проходов score < 8 — зафиксировать как "⚠️ accepted at {N}/10" и перейти дальше.

После завершения цикла покажи итоговую таблицу с обновлёнными scores и спроси: "Все файлы обработаны. Применяю исправления?"

### Фаза 4: Диалог по оставшимся находкам

Если после Фазы 3.5 остались находки из Фазы 2, которые не были покрыты scoring-итерацией (например, cross-cutting проблемы в `00-overview.md`, или проблемы графа зависимостей):

Для каждой такой находки:
1. Покажи проблему подробно: что не так, где, почему это важно.
2. Предложи решение (варианты, если их несколько).
3. Дождись ответа пользователя:
   - **Принять** — исправление добавляется в очередь.
   - **Отклонить** — находка игнорируется (пометить как "отклонено пользователем").
   - **Уточнить** — задай дополнительный вопрос, переформулируй решение.
4. Перейди к следующей находке.

### Фаза 5: Применение исправлений

1. Покажи **итоговый diff** всех принятых исправлений (из Фаз 3.5 и 4):
   ```
   Принятые исправления ({N} из {M} находок):

   [ОБНОВИТЬ] 02-1-domain-model.md (score: 5 → 9)
     - Секция 1: путь исправлен pkg/sast/policy.go → pkg/sast/security_policy.go
     - Добавлена ссылка на существующий паттерн из model.go

   [ОБНОВИТЬ] 03-2-issue-history.md (score: 6 → 8)
     - Добавлена секция 5: Unit-тесты (или ссылка на отдельную задачу)

   [ОБНОВИТЬ] 00-overview.md
     - Граф: добавлена связь 4.1 → 4.2

   Отклонено: {K} находок
   Общий score: {X.X}/10 → {Y.Y}/10
   ```
2. Дождись подтверждения пользователя.
3. Запиши изменения в файлы.
4. Обнови `00-overview.md` если затронут граф, карта файлов или итоги.
5. Обнови `.context.md`:
   - Секция 3: добавь решения review (принятые и отклонённые с обоснованием).
   - **Секция 5.5**: запиши итоговые quality scores по шаблону из `~/.claude/kirpr/config/templates.md`.
   - Секция 7: обнови дату последней адаптации.

## Дополнительные правила review

- **Показывай доказательства.** Каждая находка подкреплена конкретной цитатой из файла или результатом проверки кодовой базы.
- **Severity обоснован.** `Критично` = блокирует реализацию. `Важно` = приведёт к переделке. `Замечание` = можно улучшить.
