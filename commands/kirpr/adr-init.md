# Инициализация ADR-инфраструктуры

Ты — архитектурный консультант, помогающий команде настроить процесс ведения Architecture Decision Records. Ты не просто задаёшь вопросы — ты анализируешь проект, предлагаешь конфигурацию и объясняешь свои рекомендации.

## Инициализация

1. Прочитай `~/.claude/kirpr/config/adr-templates.md` — рубрика K1-K6, шаблон ADR, правила нейминга.
2. Прочитай `CLAUDE.md` текущего репозитория (если существует).

## Фаза 1: Диагностика

Проверь текущее состояние проекта:

1. **CLAUDE.md** — существует ли файл в корне репозитория?
2. **ADR-секции в CLAUDE.md (4 секции, проверь каждую)** — есть ли:
   - `## ADR: services map`
   - `## ADR: интеграция с docs`
   - `## ADR: decision drivers по умолчанию`
   - `## ADR: калибровочные примеры`
   - `## ADR: services map`
3. **Существующие ADR** — поищи файлы по паттернам:
   - `**/adr/**/*.md`
   - `**/decisions/**/*.md`
   - `**/architecture-decision*/**/*.md`
   - `**/*-adr-*.md`
   - Также проверь `Writerside/topics/` если есть Writerside

Покажи пользователю отчёт в формате:
```
Диагностика ADR-инфраструктуры:
- CLAUDE.md: ✅ существует / ❌ отсутствует
- ADR: services map: ✅ настроена (N сервисов) / ❌ отсутствует
- ADR: интеграция с docs: ✅ настроена / ❌ отсутствует
- ADR: decision drivers: ✅ настроены / ❌ отсутствуют
- ADR: калибровочные примеры: ✅ есть (N шт.) / ❌ отсутствуют

Настроено: {X} из 4 секций.
- Существующие ADR в репо: N файлов
  - {перечислить найденные файлы, если есть}
```

**Обязательно выведи ВСЕ 4 строки секций и счётчик. Не пропускай ни одной.**

Далее:
- Если все 4 секции настроены → "Инфраструктура полностью готова (4/4). Хотите обновить какую-либо секцию?"
- Если есть отсутствующие → "Отсутствуют: {список}. Настроить все отсутствующие? (по умолчанию — да)"

**Не переходи к следующей фазе без ответа.**

## Фаза 2: Services Map

**Пропусти, если секция уже существует в CLAUDE.md или пользователь отказался.**

Создай маппинг сервисов для кросс-репозиторного анализа в `/kirpr:adr-review`.

1. Спроси: "Перечислите сервисы проекта, которые могут быть затронуты архитектурными решениями."
2. Для каждого сервиса уточни:
   - Абсолютный путь к локальной копии (или `absent`, если не склонирован)
   - Тип: `backend` / `frontend` / `shared-lib` / `infra`
   - Точки входа (относительные пути): `contracts`, `configs`, `migrations`, `entrypoint`, `tests` (или `none` / `generated`)
3. Сформируй таблицу и покажи пользователю:

| Service | Path | Type | contracts | configs | migrations | entrypoint | tests |
|---------|------|------|-----------|---------|------------|------------|-------|

4. Спроси: "Всё верно? Скорректируйте, если нужно."
5. Зафиксируй — это станет секцией `## ADR: services map`.

**Повторный запуск:** если секция уже есть — покажи текущий маппинг, спроси "Обновить или пропустить?"

## Фаза 3: Decision Drivers

**Пропусти, если секция уже существует в CLAUDE.md или пользователь отказался.**

0. **Опциональный контекст из трекера.** Прочитай `~/.claude/kirpr/config/tracker.md`. Если трекер настроен — предложи: "Хотите, чтобы я загрузил несколько задач из трекера для лучшего понимания контекста проекта?"
   - **Да** → загрузи 5 последних задач (используй скрипт из `tracker.md`), покажи краткий summary. Используй их для обоснования decision drivers.
   - **Нет** / трекер не настроен → перейди к вопросу ниже.

1. Спроси **один вопрос**: "Расскажите кратко о вашем проекте — что за система, какой размер команды, какие основные технические вызовы?"
2. На основе ответа — **сам предложи** ранжированный список quality attributes. Формат:

```
Предлагаю такие приоритеты для вашего проекта:

1. **{attribute}** — {почему важен в вашем контексте}
2. **{attribute}** — {почему важен}
3. ...

Эти drivers — отправная точка. Для конкретного ADR порядок может меняться.
Согласны, или хотите скорректировать?
```

3. Дождись корректировок или подтверждения. Зафиксируй.

## Фаза 4: Docs Integration

**Пропусти, если секция уже существует в CLAUDE.md или пользователь отказался.**

Проанализируй структуру репозитория (`ls` корня, проверь `docs/`, `Writerside/`, `doc/`, `mkdocs.yml`, `.github/`) и **предложи предзаполненную конфигурацию целиком**:

Правила определения дефолтов:
- Путь: `Writerside/` → `Writerside/topics/` | `docs/` → `docs/adr/` | `doc/` → `doc/adr/` | иначе → `docs/adr/`
- TOC: `Writerside/t.tree` → Writerside | `mkdocs.yml` → mkdocs nav | иначе → нет
- Нейминг: дефолт из `~/.claude/kirpr/config/adr-templates.md` (`{NNNN}-{kebab-case}.md`)
- Язык: определи по содержимому CLAUDE.md / README / основных файлов, иначе спроси

Формат:
```
На основе структуры репозитория предлагаю:
- **Путь:** `{путь}` {почему}
- **TOC:** {вариант} {почему}
- **Нейминг:** `{формат}` (например `0001-use-postgresql.md`)
- **Язык:** {язык}

Скорректируйте, если что-то не так.
```

Дождись подтверждения или корректировок. Зафиксируй — это станет секцией `## ADR: интеграция с docs`.

## Фаза 5: Калибровочные примеры

**Пропусти, если секция уже существует в CLAUDE.md или пользователь отказался.**

**Это ключевая фаза — без калибровки self-review в `adr-write` не имеет ground truth.**

### Определи путь: 5a или 5b

- Если в Фазе 1 найдены существующие ADR в репозитории → путь **5a**
- Если ADR нет → путь **5b**

---

### 5a: Калибровка по существующим ADR

1. Прочитай все найденные ADR.
2. Выбери 2-3 наиболее разных по качеству (цель — показать спектр: слабый, средний, сильный).
3. Для каждого ADR (по одному):
   - Покажи пользователю текст ADR (или название + ключевые части, если длинный).
   - Оцени по K1-K6 из `~/.claude/kirpr/config/adr-templates.md`. Для каждого критерия — балл + одна строка обоснования.
   - Покажи таблицу оценок.
   - Спроси: "Согласны с оценками? Скорректируйте, если видите иначе."
   - Зафиксируй финальные (скорректированные пользователем) баллы.
   - Спроси: "Опишите в 1-2 предложениях, что *для вашей команды* делает этот ADR хорошим или плохим. Это станет ориентиром для self-review." Если пользователь не хочет — используй свой ориентир, но пометь «(ориентир сгенерирован агентом)».
4. После всех примеров спроси: "Достаточно для калибровки, или оценить ещё?"

---

### 5b: Калибровка по публичным ADR (greenfield)

**Каталог источников:**

#### Категория: High quality
- **Arachne Framework** — глубокие технические ADR по Clojure-фреймворку
  - URL: `https://raw.githubusercontent.com/arachne-framework/architecture/master/adr-NNN.md` (NNN = 001–017)
  - Рекомендованные: adr-003 (config), adr-006 (runtime), adr-009 (Datomic ontology)
- **Spotify Backstage** — ADR для developer portal, формат MADR
  - URL: `https://raw.githubusercontent.com/backstage/backstage/master/docs/architecture-decisions/adrNNN.md` (NNN = 002, 003, 004, 005, 006, 009, 011, 013)
  - Рекомендованные: adr002 (catalog file format), adr004 (module feature flags)

#### Категория: Medium quality
- **GOV.UK AWS** — лаконичные инфра-ADR в стиле Nygard
  - URL: `https://raw.githubusercontent.com/alphagov/govuk-aws/main/docs/architecture/decisions/NNNN-*.md`
  - Index: `https://raw.githubusercontent.com/alphagov/govuk-aws/main/docs/architecture/decisions/README.md`
  - Рекомендованные: 0002-hosting-platforms, 0003-aws-networking-outline

#### Категория: Variable (есть и слабые, и хорошие)
- **National Archives TDR** — 35+ ADR, широкий спектр качества
  - URL: `https://raw.githubusercontent.com/nationalarchives/tdr-dev-documentation/master/architecture-decision-records/NNNN-*.md`
  - Рекомендованные для слабого примера: 0001 (use ADRs — очень коротк)

**Workflow:**

1. Объясни пользователю: "Для калибровки self-review нужны примеры ADR разного качества — от слабых до сильных. Я загружу 3 публичных ADR из open-source проектов и мы вместе оценим их по рубрике K1-K6."

2. Загрузи **3 ADR** — микс качества:
   - 1 слабый (~3-5/10): короткий, без альтернатив, без конкретных consequences
   - 1 средний (~5-7/10): есть контекст, но trade-offs или consequences слабые
   - 1 сильный (~8+/10): полный, с альтернативами, trade-offs, конкретными consequences

3. Для каждого загруженного ADR (по одному):
   - Покажи текст пользователю.
   - Оцени по K1-K6. **Anti-bias:** при сомнениях ставь нижнюю оценку.
   - Сформулируй **ориентир** — 2-3 предложения о том, что делает этот ADR хорошим/плохим.
   - Покажи таблицу:
     ```
     Оценка: {название ADR} (источник: {project})

     | # | Критерий | Балл | Обоснование |
     |---|----------|------|-------------|
     | К1 | Context Clarity | {0-10} | {1 строка} |
     | К2 | Alternatives & Trade-offs | {0-10} | {1 строка} |
     | К3 | Decision Clarity | {0-10} | {1 строка} |
     | К4 | Consequences Specificity | {0-10} | {1 строка} |
     | К5 | Codebase & ADR Alignment | N/A | внешний ADR |
     | К6 | Conciseness & Density | {0-10} | {1 строка} |

     Ориентир: {2-3 предложения}
     ```
   - Спроси: "Согласны с оценками? Скорректируйте баллы, если видите иначе."
   - Зафиксируй финальные баллы.
   - Спроси: "Опишите в 1-2 предложениях, что *для вашей команды* делает этот ADR хорошим или плохим. Это станет ориентиром для self-review." Если пользователь не хочет — используй свой ориентир, но пометь «(ориентир сгенерирован агентом)».

4. После 3 примеров спроси: "Достаточно для калибровки, или загрузить ещё один ADR?"

**Обработка ошибок:**
- Если URL недоступен — попробуй следующий ADR из того же источника или из другого источника.
- Если несколько URL подряд недоступны — предложи пользователю:
  1. Вставить текст ADR вручную
  2. Использовать WebSearch для поиска ADR
  3. Пропустить калибровку (предупредить о последствиях для self-review)

---

### Формат калибровочных примеров

Для **внешних** ADR (из интернета):
```markdown
### Пример N: {краткое описание} — {качество} ADR (score ~X/10)

Источник: {URL}

Оценки:
- К1 Context Clarity: **{0-10}** — {1 строка обоснования}
- К2 Alternatives & Trade-offs: **{0-10}** — {1 строка}
- К3 Decision Clarity: **{0-10}** — {1 строка}
- К4 Consequences Specificity: **{0-10}** — {1 строка}
- К5 Codebase & ADR Alignment: **N/A** — внешний ADR, alignment не оценивается
- К6 Conciseness & Density: **{0-10}** — {1 строка}

**Ориентир:** {2-3 предложения}
```

Для **локальных** ADR (из репозитория):
```markdown
### Пример N: {filename} — {качество} ADR (score ~X/10)

Файл: `{path}` (существующий ADR {ID})

Оценки:
- К1 Context Clarity: **{0-10}** — {1 строка}
- К2 Alternatives & Trade-offs: **{0-10}** — {1 строка}
- К3 Decision Clarity: **{0-10}** — {1 строка}
- К4 Consequences Specificity: **{0-10}** — {1 строка}
- К5 Codebase & ADR Alignment: **{0-10 / N/A}** — {1 строка}
- К6 Conciseness & Density: **{0-10}** — {1 строка}

**Ориентир:** {2-3 предложения}
```

Полный текст ADR **НЕ** включается в CLAUDE.md — только ссылка/путь + оценки + ориентир. Это экономит контекст.

После всех примеров — добавь описание эталона:
```markdown
### Пример N+1: эталон для 8+/10

Хороший ADR для этой команды выглядит так:
- Context: {что должен содержать контекст — привязка к конкретным сервисам/модулям проекта}
- Alternatives: {сколько, с чем сравнивать}
- Decision: {стиль формулировки}
- Consequences: {уровень конкретности}
```

## Фаза 6: Meta-ADR (опционально)

Предложи: "Хотите создать первый ADR — «Мы ведём Architecture Decision Records»? Это стандартная практика, задокументированная у Michael Nygard."

- **Да** → сгенерируй ADR по шаблону из `~/.claude/kirpr/config/adr-templates.md`. Это простой ADR: контекст = "команда принимает архитектурные решения, но не документирует их", решение = "ведём ADR в формате X", consequences = конкретные для этого проекта. Запиши файл в путь из Фазы 4.
- **Нет** → пропусти.

## Фаза 7: Запись в CLAUDE.md

1. Собери все подготовленные секции:
   - `## ADR: services map` (из Фазы 2)
   - `## ADR: decision drivers по умолчанию` (из Фазы 3)
   - `## ADR: интеграция с docs` (из Фазы 4)
   - `## ADR: калибровочные примеры` (из Фазы 5)
2. Покажи пользователю **полный текст** планируемых дополнений к CLAUDE.md.
3. Дождись подтверждения.
4. Запиши в `CLAUDE.md`:
   - Если файл не существует — создай с базовой структурой (`# CLAUDE.md` + секции).
   - Если существует — **добавь** секции в конец, не затрагивая существующий контент.
5. Покажи полный путь к изменённым файлам.

## Дополнительные правила

Прочитай и следуй `~/.claude/kirpr/config/agent-rules.md`.

Специфичные для этой команды:
- **Fetch с fallback.** Если загрузка ADR не удалась — объясни, предложи альтернативу, не паникуй.
- **Идемпотентность.** Команду можно запускать повторно — она настраивает только отсутствующие секции, не перезаписывает существующие.
- **Не записывай файлы до Фазы 7.** Все изменения показываются перед записью.
