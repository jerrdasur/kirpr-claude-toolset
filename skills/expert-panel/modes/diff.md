# Режим: ревью diff

Разбор изменений перед коммитом или merge request.

## Preflight

1. Убедись, что текущий каталог внутри git-репозитория: `git rev-parse --git-dir`. Не репозиторий — сообщи и прерви.
2. Разбери аргументы. Сначала извлеки `--spec <путь>` вместе с его значением — базой считается только оставшийся позиционный аргумент.
   - `--spec` указан, но файла по пути нет — сообщи и спроси путь. Не продолжай молча: сверка со спекой — половина смысла вызова.
   - База осталась — разреши её по шагу 3.
   - Базы нет — сравнивай рабочее дерево с `HEAD`, шаг 3 пропусти.
3. Разреши базу в ref и проверь актуальность. Ни одна из команд не предполагается успешной — проверяй каждую:

       git rev-parse --verify <база>
       git remote get-url origin

   - Локального ref нет, но есть `origin/<база>` — ревьюй против `origin/<база>` и скажи об этом пользователю.
   - Нет ни локального ref, ни `origin/<база>` — сообщи, что база не найдена, и прерви.
   - `origin` отсутствует — проверку свежести пропусти, предупреди, что база не сверена с удалённой, и продолжай. Репозиторий без remote — нормальный случай, а не ошибка.
   - Локальный ref есть, но `origin/<база>` нет — база это тег, SHA или ветка без upstream. Проверку свежести пропусти, скажи об этом и продолжай.
   - `origin` и оба ref есть — выполни:

         git fetch origin <база> --quiet
         git rev-list --count <база>..origin/<база>

     Результат больше нуля — локальная база отстала. Спроси пользователя: обновить базу или ревьюить против устаревшей. Молча ревьюить неверный diff хуже, чем не ревьюить вовсе.
4. Собери список изменённых файлов (`git diff --name-only` с той же базой, что и в шаге 5) и примени фильтры по секции «Фильтрация файлов» — до получения diff, а не после. Фильтр, применённый к отчёту, но не к diff, — это ложь пользователю: агенты всё равно прочитают исключённое и будут на него ссылаться.
5. Получи diff, ограниченный оставшимися путями, и сохрани во временный файл — агентам передаётся путь, а не содержимое в промпте:
   - без базы: `git diff HEAD -- <оставшиеся пути>`;
   - с базой: `git diff <разрешённая база>...HEAD -- <оставшиеся пути>` — три точки, сравнение от точки расхождения. Незакоммиченные изменения сюда не попадают; если рабочее дерево грязное, скажи об этом пользователю.
6. **Неотслеживаемые файлы.** `git diff` их не видит ни в одном из вариантов, а перед коммитом новый файл — самый частый вид изменения. Получи их списком:

       git status --porcelain

   Строки со статусом `??` покажи пользователю и спроси: включить в ревью или пропустить. Включённые передаются агентам отдельным списком путей — агенты читают такой файл целиком, не как diff. Фильтры из следующей секции применяй и к ним. Индекс не трогай: `git add -N` — запись, а скил до согласия пользователя ничего не пишет.
7. Если не осталось ни отслеживаемых изменений после фильтрации, ни включённых неотслеживаемых файлов — сообщи и прерви. Проверять это раньше шага 6 нельзя: рабочее дерево, где единственное изменение — новый файл, иначе оборвётся с «нет изменений» ровно в том сценарии, ради которого шаг 6 и существует.

## Фильтрация файлов

Фильтры применяются к списку файлов до получения diff. Исключай три категории:

1. **Сгенерированный Go-код** — файлы, где строка вида `// Code generated ... DO NOT EDIT.` встречается до первой непустой некомментарной строки. Не обязательно первая строка файла: выше могут быть лицензионная шапка и `//go:build`.
2. **Дефолтный список путей:** `vendor/`, `*.pb.go`, `*_mock.go`, `testdata/`.
3. **Проектный список** — если в репозитории есть `.claude/expert-panel-ignore`, каждая непустая строка без `#` в начале трактуется как шаблон. Набор генераторов у каждой команды свой, это свойство проекта, а не скила.

Семантика шаблонов в обоих списках одинакова: путь берётся от корня репозитория; шаблон с завершающим `/` — префикс каталога; в остальном обычный glob по всему пути, поэтому `*.pb.go` совпадает на любой глубине.

Покажи пользователю, сколько файлов исключено и по какой причине. Молчаливое исключение читается как «панель это посмотрела».

## Фаза 1. Контекст

1. Список изменённых файлов со статистикой и список включённых неотслеживаемых файлов.
2. Для каждого файла из diff читай контекст целиком, а не только изменённые строки. Ревьюится только diff, но судить о нём без окружения нельзя. Неотслеживаемые файлы читаются целиком — там нет «изменённых строк», весь файл новый.
3. Если передан `--spec <путь>` — прочитай спеку и её `## Review log`.
4. Покажи summary: база и как она разрешена, число файлов, исключённые файлы с причинами, судьба неотслеживаемых, наличие спеки.

**Не переходи к Фазе 2 без подтверждения пользователя.** Это единственный момент, когда можно поправить базу или список исключений до запуска N параллельных агентов.

## Фаза 2. Панель

Собери активную панель и запусти агентов по протоколу из `SKILL.md`. Режим — `diff`: агент использует блок «В diff проверяет» своей персоны.

Каждому агенту передай: путь к файлу с diff, список изменённых файлов, список включённых неотслеживаемых файлов с пометкой «читать целиком», путь к спеке и её Review log, если передан `--spec`.

При `--spec` каждый агент дополнительно проверяет:
- что из спеки не реализовано;
- что сделано сверх спеки;
- какие решения, зафиксированные в Review log, нарушены.

## Фаза 3. Отчёт

Синтезируй по протоколу из `SKILL.md`. Каждое замечание обязано иметь `file:line`.

1. **Панель** — кто участвовал, база, число файлов.
2. **Удачные решения** — обязательно, если есть за что. Отчёт из одних претензий перестают читать.
3. **Замечания** — по убыванию severity.
4. **Конфликты**.
5. **Ниже порога**.
6. **Что не смотрели** — исключённые файлы, пропущенные неотслеживаемые, всё, что не попало в diff. Вердикт имеет вес, и он не должен выноситься над необъявленным слепым пятном.
7. **Вердикт** — `Approve`, `Approve with comments` или `Request changes`. При `Request changes` перечисли блокеры списком.

## Фаза 4. Разбор

Тот же формат, что в режиме спеки:

    accept C2,S1; reject F3 — причина; ? P4

## Фаза 5. Правки

1. Применяй только принятые замечания.
2. Тесты, линтеры и сборку не запускай — выведи команды, которые пользователь запустит сам. Панель судит о коде, а не отвечает за то, что он собирается.
3. Покажи diff внесённых правок.
4. Коммит не делай.
