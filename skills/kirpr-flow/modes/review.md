# modes/review.md — заказ ревью

Ручная точка входа в ревью: вызывается, когда нужна проверка кода вне
автоматического цикла `modes/execute.md`, где ревью после задачи и
финальное ревью происходят сами, без отдельного вызова этого режима.
Механизм тот же в обоих случаях — заполненный `prompts/code-reviewer.md`
и субагент, читающий файлы целиком, — этот файл описывает, как собрать
такой запрос вручную.

## Аргумент

Либо путь к каталогу плана — тогда список файлов собирается из ledger;
либо перечень путей через пробел. Нет аргумента — спросить, что
ревьюить. Не угадывать: без git список изменённых файлов взять неоткуда.

Когда аргумент — путь к каталогу плана: список файлов — объединение
секций «Файлы» из всех строк ledger вида «готово» на текущий момент,
каждый путь один раз, — тот же принцип, что использует финальное ревью в
`modes/execute.md`.

## Когда заказывать ревью

Обязательно: после каждой задачи в режиме `execute`; после крупной
функциональности. Полезно: когда работа встала; перед перестройкой
существующего кода.

Размер правки не сокращает список «Обязательно»: однострочная правка
проходит через тот же список, что крупная, — «правка слишком мала для
ревью» сюда не относится ни при каком объёме.

Первый пункт «Обязательно» происходит сам, внутри `modes/execute.md`, и
не требует вызывать этот режим отдельно — он назван здесь, чтобы граница
была явной: этот файл описывает ручной заказ ревью для трёх остальных
случаев — работы, сделанной вне `execute` (например, в
`execute-inline` или правкой в разговоре), крупной функциональности
целиком, и двух случаев «Полезно».

## Как заказывать

Заполнить `prompts/code-reviewer.md`: `{ЧТО_ПОСТРОЕНО}` — что построено,
`{ТРЕБОВАНИЯ}` — требования, `{СПИСОК_ФАЙЛОВ}` — список файлов,
`{ОТЛОЖЕННЫЕ_ЗАМЕЧАНИЯ}` — отложенные замечания, накопленные за работу.
Список файлов передаётся путями; содержимое файлов в промпт не
вставляется.

Модель — по таблице `core/subagents.md`: средняя модель — обязательная
нижняя граница для любого ревьюера; если объём ревью приближается к
финальному ревью всего плана, берётся самая способная из доступных, по
той же таблице.

## Почему субагент, а не сам

Чтение всех файлов набора в своём контексте съедает окно, нужное для
координации. У субагента файлы и разбор живут в его контексте, к вам
возвращаются только находки.

## Что делать с находками

`Critical` — чинить сразу; `Important` — чинить до перехода дальше;
`Minor` — записать. Возражать, если ревьюер не прав, по правилам из
`core/feedback.md`: техническое основание и ссылка на файл, а не «я
считаю иначе».

«Записать» зависит от того, каким был аргумент режима. При каталоге
плана — строкой в ledger, форматом из `core/artifacts.md`. При
перечне путей без каталога плана — ledger взять неоткуда: находки
уровня `Minor` возвращаются пользователю в том же ответе, что и находки
`Critical` и `Important`, а не откладываются в файл, которого нет.
