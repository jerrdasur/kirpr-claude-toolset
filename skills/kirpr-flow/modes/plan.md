# modes/plan.md — спека → план каталогом

Режим превращает одобренную спеку в план, разложенный по задачам, которые
потом исполняет `modes/execute.md` или `modes/execute-inline.md`. Результат
этого режима — каталог на диске, а не текст в ответе: путь и формат каталога
заданы дословно ниже и совпадают с тем, что описывает `core/artifacts.md`.

## Аргумент

Путь к спеке. Если аргумента нет — спросить, по какой спеке планируем. Не
угадывать по содержимому репозитория: непрочитанная спека — не повод
предполагать, какая из нескольких лежащих в `docs/kirpr-flow/specs/`
имелась в виду.

## Проверка объёма

Если спека покрывает несколько независимых подсистем, предложить разбить на
отдельные планы — по одному на подсистему. Каждый план должен давать
работающий и проверяемый результат сам по себе: план, который заканчивается
на середине подсистемы, оставляет пользователя без результата, который
можно проверить.

## Карта файлов до задач

Прежде чем резать спеку на задачи, выписать, какие файлы создаются и
изменяются и за что каждый отвечает. Файлы с одной ответственностью; файлы,
меняющиеся вместе, лежат вместе; в существующей кодовой базе — следовать её
образцам, а не перестраивать их по-своему. Эта карта — материал для
следующего шага, а не правило нарезки: она называет файлы и их
ответственность, а где именно проходит граница между задачами, решает не
она — решает «Размер задачи» ниже, старший критерий.

## Размер задачи

Старший критерий нарезки — этот раздел, а не карта файлов выше: карта
называет, что где лежит, а где между файлами проходит граница задачи,
решают правила отсюда. Задача — наименьшая единица, которая несёт
собственный цикл проверки и заслуживает отдельного ревью. Настройка,
конфигурация и документация
складываются внутрь той задачи, чьему результату они нужны, — они не
становятся отдельными задачами сами по себе. Резать там, где ревьюер мог бы
осмысленно отклонить одну задачу, одобрив соседнюю: если отклонение одной
неизбежно тянет за собой отклонение другой, это одна задача, а не две.

## Структура каталога плана

```
docs/kirpr-flow/plans/YYYY-MM-DD-<тема>/
  00-overview.md
  task-01.md … task-NN.md
```

`progress.md` и `reports/` создаёт режим execute, планирование их не
трогает: на момент, когда этот режим заканчивает работу, каталог плана
содержит только `00-overview.md` и файлы задач.

## Что в 00-overview.md

- Цель — одной строкой.
- Архитектура — в две-три строки.
- Стек.
- Путь к спеке, из которой построен план.
- Раздел «Глобальные ограничения» — проектные требования из спеки,
  скопированные дословно, с точными значениями, по строке на требование.
  Требования каждой задачи плана включают этот раздел неявно, даже если
  текст самой задачи его не повторяет, — поэтому формулировки здесь должны
  быть такими, чтобы задача могла на них ссылаться без пересказа.
- Карта файлов — та же, что выписана в «Карте файлов до задач», перенесённая
  в итоговый документ.
- Порядок задач, с объяснением, почему он такой: какая задача от какой
  зависит, что нужно построить раньше, чтобы следующая задача могла
  ссылаться на готовые имена и пути.

## Что в task-NN.md

Заголовок с номером и коротким именем задачи и абзац о том, где эта задача
стоит в проекте — до остальных блоков; без него исполнитель, увидевший
только файл своей задачи, не поймёт контекст, который в диалоге о
планировании был очевиден.

Дальше:

- блок «Файлы» — что создаётся, что изменяется, с указанием строк там, где
  меняется существующий файл, и какие тесты задача пишет или прогоняет;
- блок «Интерфейсы» — что задача потребляет от предыдущих задач и что
  предоставляет следующим, с точными именами и сигнатурами. Это не
  формальность: исполнитель видит только свою задачу, а не план целиком, и
  этот блок — единственное место, где он узнаёт имена и типы, которыми
  пользуются соседние задачи;
- шаги по 2-5 минут каждый, с чекбоксами `- [ ]`;
- последним шагом — верификация.

## Верификация как последний шаг

У каждой задачи последний шаг — верификация в одном из четырёх форматов, с
точной командой и ожидаемым результатом. Формат выбирается по тому, что
задача произвела, а не по тому, что исполнителю удобнее показать: код →
тест, скрипт → запуск, БД → запрос, документ → чтение целиком.

Шаг верификации без точной команды — не отдельная категория дефекта, а
частный случай «шага без конкретики» из «Запрета плейсхолдеров» ниже:
граница между двумя разделами не в типе нарушения, а в том, что один
описывает требование к последнему шагу, а второй — общий список того, чем
шаг может не дотягивать до этого требования.

## Никакого git в плане

Режим прямо запрещает вписывать в план шаги с git-операциями. Исполнитель
обязан следовать плану дословно, и шаг «закоммитить» в плане означает либо
нарушенный запрет, либо задачу, которую исполнитель не сможет закрыть: он
получит инструкцию, выполнить которую ему не позволено.

## Запрет плейсхолдеров

Дефекты плана, которых быть не должно:

- «TBD», «доделать позже»;
- «добавить обработку ошибок», «добавить валидацию» — без того, что именно
  добавляется;
- «написать тесты для вышеописанного» без самих тестов;
- «аналогично задаче N» вместо повторения содержания — исполнитель читает
  задачи не по порядку и может не иметь задачи N перед глазами;
- шаги без конкретики там, где нужен код;
- ссылки на имена, не определённые ни в одной задаче плана.

## Самопроверка

Формат «документ»: прочитать каждый файл плана целиком и проверить покрытие
спеки, плейсхолдеры, согласованность имён и типов между задачами. Найденное
чинится на месте, без отдельного раунда — самопроверка это часть написания
плана, а не ревью постфактум.

## Проверка субагентом

Опционально: заполнить `prompts/plan-reviewer.md` и запустить проверку
плана отдельным агентом. Подстановки шаблона: {ПУТЬ_К_ПЛАНУ} — путь к
каталогу только что написанного плана, {ПУТЬ_К_СПЕКЕ} — путь к спеке из
раздела «Аргумент» этого режима. Найденное ревьюером чинится тем же
способом, что и находки самопроверки.

## Передача дальше

Предложить два пути:

- `execute` — свежий субагент на задачу, с ревью между задачами;
  рекомендуемый путь.
- `execute --inline` — исполнение в текущей сессии, без субагентов, для
  случая, когда субагенты недоступны.

Выбор — за пользователем.
