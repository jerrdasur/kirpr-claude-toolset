# modes/execute-inline.md — исполнение без субагентов

Запасной путь исполнения плана `kirpr-flow`: та же дисциплина задача за
задачей и тот же ledger, что в `modes/execute.md`, но без диспетча
субагентов — вся работа идёт в текущей сессии.

## Когда этот режим

Режим предназначен для случая, когда субагенты недоступны. Если
пользователь просит именно этот режим при доступных субагентах — сказать
одной строкой, что `modes/execute.md` даёт свежий контекст на каждую задачу
и отдельное ревью между задачами, которых `execute-inline` не даёт, и
исполнить то, что просят. Предупреждение — один раз; дальше не спорить и не
возвращаться к нему на каждой задаче.

## Аргумент

Путь к каталогу плана. Если аргумента нет — спросить, какой план исполняем.

## Порядок

1. Сказать пользователю прямым текстом: изоляции нет, работа идёт в текущем
   рабочем дереве, за его состояние отвечает пользователь.
2. Прочитать `00-overview.md` и все файлы задач целиком — не выборочно и не
   по мере надобности, а весь план до начала работы.
3. Прочитать план критически: выписать вопросы и сомнения — пробелы в
   покрытии, противоречия между задачами, шаги без конкретики.
4. Если сомнения есть — поднять их с пользователем до начала работы. Не
   начинать первую задачу, пока открытые вопросы не закрыты.
5. Создать todo на каждую задачу плана.
6. Исполнять задачи по порядку: шаги каждой задачи — дословно, в том
   порядке, в котором они написаны; верификация не пропускается ни для
   одной задачи. Для задач, производящих код, — цикл из `core/tests.md`:
   тест первым, красный прогон, минимальная реализация, зелёный прогон.
7. Вести `progress.md` в том же формате, что `modes/execute.md`: первая
   строка называет план, записи используют те же формы строк из
   `core/artifacts.md`.

## Контрольные точки

После каждой задачи — доказательство того формата, который задача
производит, и строка в ledger. В этом режиме нет отдельного ревьюера:
роль, которую в `modes/execute.md` играет ревью субагентом, здесь играет то
же перечитывание задачи, которым имплементер обычно завершает свою работу
— сверка сделанного с текстом задачи пункт за пунктом, без пропущенного и
без сделанного сверх требуемого. Строка «готово» пишется, когда эта сверка
и верификация обе пройдены — форма из `core/artifacts.md` с закрывающим
полем `самопроверка`, а не `ревью чисто`: ревью в этом режиме никто не
проводил, и строка не должна утверждать обратное. Пользователю показывается
краткий итог задачи, работа продолжается без вопроса «продолжать ли».

## Когда остановиться и спросить

Два набора условий, оба обязательны.

Первый — общий с `modes/execute.md`, скопирован из его раздела «Остановки»
дословно: необратимая или разрушительная операция; действие, затрагивающее
безопасность; побочный эффект вне рабочего дерева, о котором принято
спрашивать; план, сломанный настолько, что любой путь вперёд — догадка.
Последний пункт — про план целиком: исполнять нечего ни по одной задаче, а
не про то, что не хватает данных для одной из них (это второй набор ниже).
Этот набор из четырёх условий дублирован дословно, а не дан ссылкой на
`modes/execute.md`, и правится в обоих местах сразу: цена того, что
читатель не откроет соседний файл, здесь не «прочитал неточную
формулировку», а «не остановился перед разрушительной операцией» — тот же
довод, по которому выжимка правил дублируется в шесть файлов
`prompts/*.md` вместо ссылки. Оба режима работают в текущем рабочем дереве
без изоляции, значит по риску разрушительной операции они одинаковы, и
защита у них обязана быть общей. Хорошо описанный шаг плана «удалить
каталог» или разрушительный запрос к БД не блокер, не пробел плана и не
падение верификации — по «Порядку» он просто исполнится, если не
остановить его этим набором раньше.

Второй — специфичный для исполнения без субагентов, он компенсирует
отсутствие эскалации через диспетч: в `execute` эти случаи закрывает статус
`BLOCKED` от имплементера, здесь возвращать такой статус некому.
- Блокер: недостающая зависимость, падающая верификация, непонятная
  инструкция.
- Критические пробелы в плане, не дающие начать задачу — не про план
  целиком (это первый набор выше), а про одну конкретную задачу, которой
  не хватает данных, чтобы начать именно её: неопределённый интерфейс,
  отсутствующий файл, шаг, ссылающийся на то, чего в плане нет.
- Верификация, падающая повторно после исправления — то есть попытка
  починить уже была и не сработала, а не первая же попытка её запустить.
  Верификация, не прошедшая один раз и тут же починенная понятной правкой,
  — обычный шаг работы по «Порядку», а не повод для остановки; граница
  именно в повторности после починки, а не в самом факте падения.

Ни один из шести случаев не продавливается догадкой — задача
останавливается, и вопрос идёт пользователю раньше, чем следующая попытка.

## Финал

После последней задачи — переход в `modes/finish.md`.
