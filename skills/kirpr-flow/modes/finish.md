# modes/finish.md — сводка по работе

Финальная точка исполнения плана: собирает итог и отдаёт его пользователю в
пяти частях. Это единственный режим набора, который ничего не пишет и не
чинит, — только читает то, что уже накоплено, и пересобирает в сводку.

## Что делает

Собирает итог работы над планом и отдаёт его пользователю: что сделано,
какие решения были приняты за него, что отложено, какие файлы затронуты,
что не сделано. Не трогает git: ни коммитов, ни веток, ни слияний, ни
предложений их сделать — интеграция сделанного в основную ветку остаётся
пользователю, вне границ этого набора.

## Источник данных

Аргумент режима — путь к каталогу плана, тот же, что принимают
`modes/execute.md` и `modes/execute-inline.md`. Когда `finish` приходит по
разделу «Финал» одного из этих режимов, каталог уже известен из текущей
сессии — спрашивать его заново не нужно. При прямом вызове без аргумента —
спросить, какой план завершаем.

Режим не принимает ничего, кроме этого пути. Всё остальное — файлы,
доказательства верификации, решения, отложенные находки, включая все
строки `Решение:` из «Разбора плана до старта», предохранителя и
финального ревью в `modes/execute.md`, — он находит сам, читая
`progress.md` в этом каталоге. Отдельного канала передачи между режимами
нет: `modes/execute.md` ничего для этого перехода не готовит.

`progress.md` в этом каталоге — обязательный источник, отчёты в `reports/`
— дополнительный. Режим обязан работать и без них: при исполнении через
`modes/execute-inline.md` отчётов не существует, потому что нет отдельного
исполнителя, который бы их писал. Всё необходимое для сводки есть в
строках ledger: затронутые файлы, доказательство верификации, решения,
отложенные находки. Отчёты, когда они есть, дают подробности, а не основу
— часть 4 ниже называет, где именно они уточняют список файлов.

Рабочее дерево не сканируется: без git отличить свою правку от чужой
нельзя, и сводка честно говорит, что собрана из журнала и, где они есть,
из отчётов, — а не из состояния файлов на диске.

## Пять частей сводки

По абзацу на каждую.

1. **Сделанное.** Задачи, файлы и результат верификации — по каждой
   задаче, дошедшей до строки закрытия, во всех трёх формах из
   `core/artifacts.md`: `ревью чисто`, `самопроверка`, `отложено K`. Форма
   закрытия идёт в сводку вместе с остальным содержанием строки — она
   сообщает, проверял ли задачу кто-то кроме исполнителя.

2. **Решения, принятые за пользователя.** Все строки, у которых слово
   `Решение:` стоит сразу после номера задачи или в начале строки без
   номера, — формы `Задача N: Решение: <находка> — <что решено и почему>`
   и `- Решение: <что решено> — <почему> — <цена ошибки>` из
   `core/artifacts.md`, в порядке принятия, каждая с ценой ошибки. Список
   исчерпывающий: решение, оставшееся только в ledger и не попавшее в
   сводку, было принято втайне. Сюда не входит форма `Задача N: отложено —
   <находка> — Решение: <почему код остаётся>` — слово «Решение» там
   объясняет, почему находку не стали чинить, а не фиксирует отдельное
   решение; такая строка идёт в часть 3, а не в эту.

3. **Отложенные замечания.** Все строки `Задача N: minor (отложено):
   <одна строка>` и `Задача N: отложено — <находка> — Решение: <почему код
   остаётся>` — каждая с указанием файла: когда файл не назван в самой
   строке, ориентир — список файлов той же задачи из части 1.

4. **Файлы.** Объединение полей `файлы: ...` из строк ledger — список
   собран из журнала и потому доступен без `reports/`. Отчёты, где они
   есть, уточняют деление на созданное, изменённое и удалённое — сводка
   помечает, для каких файлов уточнение из отчёта есть, а для каких список
   остался плоским.

5. **Несделанное и почему.** Задачи, не дошедшие до строки закрытия: ещё
   не начатые, застрявшие на статусе `BLOCKED`, задачи, чей цикл правок не
   дошёл до предохранителя, или задачи, переоткрытые находкой и ещё не
   закрытые новой строкой «готово». Причина — по последней относящейся к
   задаче строке ledger.

**Определение статуса задачи по ledger.** Читается независимо от
остального текста этого файла: `modes/finish.md` использует его для частей
1 и 5, но правило годится для любого места набора, которому нужно понять
по `progress.md`, закрыта задача или нет, — например для раздела
«Восстановление по ledger» в `modes/execute.md`, у которого та же
уязвимость.

Базовое правило — позиционное: статус берётся по последней строке **формы
закрытия или раунда** (`готово`, `раунд правок R/5`) с номером задачи, а не
по последней строке с этим номером вообще — строки-аннотации (`Решение:`,
`minor (отложено)`) статус не меняют. Оно верно, когда журнал ведётся по
правилу `core/artifacts.md` («Формат строк ledger»): строки дописаны в
конец, порядок строк совпадает с порядком событий, записанное не
переписывается и не переставляется. При этом условии «последняя по
позиции» и есть «последняя по времени».

Исключение одно, и оно не пытается распознать нарушенный порядок по
косвенным признакам: у каждого такого признака в этой же работе на практике
находился обходной случай, который его не задевал, — наращивать признаки
дальше значит просто откладывать следующий такой случай. Вместо этого —
грубая, но решающая проверка: если для задачи в журнале есть хотя бы одна
строка, сообщающая о её переоткрытии, или больше одной строки `готово` с её
номером, — статус автоматически не выдаётся вовсе, ни в часть 1, ни в часть
5. Вместо статуса режим показывает пользователю все строки этой задачи по
порядку их появления в файле и спрашивает прямо: задача закрыта или нет.

Причина — переоткрытие редкое событие, и это ровно тот случай, где стоит
посмотреть глазами, а не доверять автоматике. Правило нарочно избыточное:
оно потребует подтверждения даже там, где журнал вёлся правильно и статус
очевиден без вопроса, — это осознанная цена. Ложное срабатывание стоит
пользователю одного вопроса; пропуск стоит сводки, которую нельзя отличить
от верной, не проверив журнал самому.

Строка, сообщающая о переоткрытии именно этой задачи, — не любое упоминание
слова «переоткрытие»: строка вида «Задача N: Решение: … задача N переоткрыта
раундом M» сообщает о конкретном событии с этой задачей; строка, которая
упоминает переоткрытие как приём или ход работы вообще, ничего не сообщает
о конкретной задаче и это условие не запускает. В журнале этой работы такая
строка есть буквально: `Задача 6: Решение:` перечисляет переоткрытие как
один из трёх ходов реальной работы, которые не были описаны в
`modes/execute.md`, — и не сообщает о переоткрытии самой задачи 6.

Задача, у которой строк формы закрытия нет вовсе, в часть 5 попадает как
незавершённая; задача, чей номер в журнале не встречается ни разу, — как
не начатая, и причину для неё брать неоткуда, кроме этого факта.

«В порядке принятия» в части 2 — это порядок строк в журнале, а не
гарантированный порядок принятия во времени: журнал ведётся по ходу
исполнения задач, и решение, записанное при переоткрытии более ранней
задачи, может в файле стоять раньше решений по задачам, принятых до
него. Порядок строк — приближение к порядку принятия, а не точное
совпадение с ним.

## Чего здесь нет

Ни вариантов «слить, опубликовать, оставить как есть», ни советов, что и
как коммитить. Это решения пользователя вне набора. Если пользователь
просит выполнить их прямо в разговоре — ответ по правилу «Прямая просьба»
из `core/rules.md`.

## Каталог плана не удаляется

В этом наборе он и есть запись о работе: истории изменений, куда она могла
бы переехать, нет.
