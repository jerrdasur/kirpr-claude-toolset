# core/rules.md — правила набора kirpr-flow

Единственный источник правды для двух вещей: что в наборе запрещено git-ом
и как доказывается, что работа сделана. Каждый режим и каждый промпт
субагента ссылается сюда, а не пересказывает правила своими словами.

## Запрет git

В наборе `kirpr-flow` нет ни одной git-операции — ни пишущей, ни читающей.
Запрещены:

`git add`, `git commit`, `git checkout`, `git branch`, `git diff`, `git log`,
`git status`, `git push`, `git pull`, `git merge`, `git stash`, `git rebase`,
`git worktree`, `git rev-parse`, `git clean`, `git init`.

Отдельно — чтение содержимого каталога `.git/`: заглянуть в `.git/HEAD`
или `.git/refs/` вместо команды `git` — тот же запрет, только в обход.

Отдельно — косвенные пути к тому же результату: `gh` (весь GitHub CLI,
не только `gh pr`), `jj` (Jujutsu поверх того же репозитория), MCP-инструменты
вида `mcp__goland__git_status` и `mcp__webstorm__git_status`. Инструмент,
который под своим именем прячет git-операцию, запрещён так же, как сам git.

Этот раздел — единственное место во всём наборе `kirpr-flow`, где
git-команды названы в форме `git <команда>` (`git commit`, `git diff` и
так далее). Формулировка сужена до этой формы намеренно: критерий приёмки
набора ищет её grep-ом, а не любое упоминание слов вроде «коммит» или
«diff» — поэтому раздел «Выжимка для промптов» ниже в этом же файле может
прозаически перечислять `commit`, `branch`, `diff`, `log`, `status` без
слова `git` перед ними, не нарушая правила.

## Когда план требует коммит

В плане, который исполняет `kirpr-flow`, шага «закоммитить» не бывает —
но если он всё же встретился (унаследован из внешнего плана, вписан
пользователем вручную), шаг пропускается. Не имитируется, не переносится
на потом — пропускается сразу, и факт пропуска уходит строкой в ledger
и в финальную сводку `modes/finish.md`.

Прямо запрещены подмены, которые на вид решают ту же задачу, что коммит,
но им не являются: архив с изменёнными файлами, копия каталога «на всякий
случай», `patch`-файл, который потом можно применить. Это обход запрета
другими средствами, а не соблюдение его. Набор оставляет изменения там,
где они лежат — в рабочем дереве, — и передаёт пользователю список файлов,
а не суррогат коммита.

## Прямая просьба

Если пользователь просит прямо в разговоре закоммитить, создать ветку
или слить изменения — набор этого не делает. Он говорит, почему: git вне
границ `kirpr-flow`, и это не техническое ограничение момента, а правило
набора. Операцию пользователь выполняет сам, вне `kirpr-flow`.

Взамен набор отдаёт то, что нужно для этой операции: список изменённых
файлов и сводку из `modes/finish.md`. Отказ без замены — это не помощь;
список файлов — то, что заменяет диф, который набор не покажет.

## Четыре формата верификации

Работа не сделана, пока не предъявлено доказательство одного из четырёх
форматов:

| Что сделано | Чем доказывается |
|---|---|
| Написан код | Тест, покрывающий этот код. Допускается временный |
| Написан скрипт | Запуск скрипта |
| Изменена БД | Запрос к БД, показывающий результат |
| Написан или обновлён документ | Чтение документа целиком |

Доказательство — это команда и её вывод. Оба нужны вместе: команда без
вывода не отличается от невыполненной команды, вывод без команды не
проверяется.

Доказательством не являются формулировки: «тесты зелёные», «должно
работать», «я проверил», «выглядит корректно». Это пересказ намерения,
а не результат его выполнения — в отчёте им не место, даже если по сути
исполнитель прав.

Для формата «документ» доказательство — это чтение файла целиком (не
куска, который писался последним) и результат по чеклисту:

- остались ли плейсхолдеры («TBD», «дополнить позже», «см. выше» вместо
  содержания);
- есть ли внутренние противоречия;
- есть ли места, которые читаются двумя способами.

## Пятый случай

Бывают изменения, к которым не подходит ни один из четырёх форматов:
правка конфига, обновление зависимости, удаление мёртвого кода. Здесь
написать «верификация неприменима» нельзя — это формулировка запрещена
явно, потому что она самая частая форма пропущенной проверки: под ней
прячется и правка, которую забыли проверить, и правка, для которой
проверку никто не искал.

Вместо неё у исполнителя два пути:

- назвать ближайший из четырёх форматов и рассказать, как именно он его
  применил к этому пятому случаю (правку конфига проверить перезапуском
  того, что конфиг читает; обновление зависимости — сборкой и тестами,
  которые от неё зависят; удаление мёртвого кода — поиском по репозиторию,
  что на него больше никто не ссылается);
- если ближайшего формата не находится — вернуть статус `BLOCKED` и
  назвать, чего не хватает.

Третьего пути — сдать работу без верификации — не существует.

## Выжимка для промптов

```
Git запрещён полностью: ни commit, ни branch, ни diff, ни log, ни status.
Если задача требует коммит — не коммить, напиши это в отчёт.
Работа не сделана, пока не предъявлено доказательство одного из четырёх
форматов: код → тест, скрипт → запуск, БД → запрос, документ → чтение целиком.
Доказательство — команда и её вывод в отчёте. Пересказ доказательством не является.
Детали: ~/.claude/skills/kirpr-flow/core/rules.md
```

Этот блок копируется в начало каждого dispatch-промпта дословно, во все
шесть файлов `prompts/*.md`. Дублирование намеренное: выжимка работает,
даже если субагент не открыл `core/rules.md` — а он может его не открыть,
потому что промпт нигде не обязывает читать файлы по ссылке до того, как
начать работу.
